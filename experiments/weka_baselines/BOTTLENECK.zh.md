# 一小时实验的瓶颈初审

2026-09-29。来源为 `results/one-hour-20260929/runs/` 的逐请求记录以及所选输入
`token_offset` 对应的实际 token 数组。属于已有时间线的分析，不是新 GPU kernel profiler 测量。

结论：复制带宽目前不是主要优化目标。迁移能改善被搬运的请求，但没有改变决定
回合完成时间的长请求。不能据此承诺优化后一定超过两种路由 baseline。

## 已核对的证据

- CacheRoute 第一次配对中，被搬运的 71,040-token 前缀，下一请求确实完整保留。
  目标相同，迁移后首 token 从 11.497s 降到 3.944s，完成从 45.803s 降到 38.316s。
  但第二轮全部完成由另一请求决定，约为 125.350s / 125.324s，基本没有改变。
- 各完整实验的第二轮关键请求均为
  `439e5f9ed3159bd826529d8ae5bd1536903f/subagent_019_7d2bf5b1/claude-fable-5`：
  输入 116,480、输出 702 tokens。CacheRoute 基线第一次 TTFT=27.988s，完成=125.350s；
  首 token 后约 97.363s，占本请求完成时间约 77.7%。这段包含生成和潜在调度/流式传输，
  不能直接等同于纯 GPU decode kernel 时间。
- 该关键请求与上一条 26,560-token 输入的实际最长公共前缀为 **0**。
  不能简单搬运前一条状态来消除它的冷 prefill。第三条输入与它的公共前缀也为 0。
  同子流/模型键不等于持续保留前缀；将这种键当作单一缓存亲和对象需要谨慎。
- 第三轮关键请求为另一个 57,920-input / 598-output 请求。CacheRoute 基线中
  已命中 54,848 tokens，TTFT=1.413s、完成=79.531s。进一步省掉少量 prefill 对
  整轮完成时间的空间有限。
- 迁移本身约 0.16–0.21s，已隐藏在公共 1 秒窗口内。再次加速传输，不会直接改善
  本轮的返回路径。搬运总量仍应作为网络/显存成本报告。

## 下一步 profiling 与优化顺序

1. 建立逐请求时间线：依赖可执行、路由排队、引擎排队、prefill、decode、复制，
   区分迁移请求收益、关键路径收益和对其他请求的影响。
2. 对 116K/702 的冷请求和 58K/598 的温热请求，分别采集单请求及混合负载短窗口
   GPU profile，定位 attention、MoE、TP collective、HBM、调度空隙的时间比例。
   通用推理优化必须同样应用于 baseline，不能当作迁移算法贡献。
3. 优先优化“移动谁、移到哪、何时移动”：用在线可观测的历史服务需求、剩余负载、
   可复用前缀与容量估计收益，而不只选长前缀。当前/未来输出长度不得以离线真值
   作为线上策略输入；同一数据集需划分训练/校准与未见测试轨迹。
4. 检查非空目标导入、繁忙源后台复制是否值得实现。它们可能扩大有效迁移覆盖面，
   但需要真实正确性和前台干扰验证，不能只删除 guard 后宣称支持。
5. 先做同 router 有/无改进的配对，再与 DualMap、CacheRoute 在相同后端、相同
   到达和输入上比较。保留跨轮缓存、失败和输出一致性审计，不选择性移除零复用轨迹。

## 成功标准

以未见过的混合轨迹上全流量 SLO goodput、尾延迟、任务完成时间的净收益为准；
迁移字节、源状态回收和干扰均计成本。若只改善可迁移请求而不能改善全局指标，
应明确限定机制用途。上述瓶颈事实支持开展 profiling，但尚不支持“优化后必胜”。
