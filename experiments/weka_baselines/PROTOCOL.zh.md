# AgentX 三节点 baseline 比较协议

## 固定矩阵与资源

- node27（6,7）、node28（4,5）、node29（0,1），每节点一个 TP2 Qwen3.6-35B-A3B BF16 引擎。
- 全局客户端最大在途请求数 BS=1、16、64、128。服务端最大 running=128；这不保证实际 GPU batch 达到 BS，必须同时报告实测 running/queued。
- 每引擎上下文 131,072、KV token slots 1,048,576、Mamba slots 384，关闭 CUDA graph。三个节点不是整机 CPU/网络独占。
- Sticky；P2C、DualMap、CacheRoute 各自的原版、加迁移、加提前重算，共 10 个方案。
- 四场景 × 四 BS × 十方案 = 160 个独立轨迹，每轨迹三轮、384 请求，共 61,440 个正式请求。
- 这是首轮矩阵，每格只有一个独立轨迹；三个 phase 不是三次独立重复，不报告虚假的大样本置信区间。

## 数据与不能声称的范围

源数据是已经校验 SHA-256 的 `cc-traces-weka-062126`，全部 98,827 请求。
46,129 条请求满足正输出且输入+输出≤131,072。按同会话/子流/模型形成连续轨迹，
不将重叠调用强行串行化；找到 1,257 条至少九个连续可执行请求的候选子流。
用固定种子 SHA 排序选择 128 条，每条九个请求，构成 1,152 条可复用输入池。

所有正式请求保留原始输入/输出长度，不设输出 cap，不截断输入。选择条件、原始
行号、请求位置、模型、原始时间、token SHA 均保存于 `data/`。各 BS 和策略使用
完全相同的场景请求与到达时间清单，不按某个策略的性能挑样本。

AgentX 不提供原始 token 文本/ID，因此以 `(conversation, model, native block ID)`
确定性映射为 64 个合法非特殊 token。保留前缀相等关系，隔离不同会话/模型，
不恢复语义。不把 Claude trace 在 Qwen 上的执行称作 Claude 性能或真实 agent 工具执行。
生成输出不用于猜造下一条原始输入；输入序列由原始 hash 轨迹确定。

短输出/短输入仅用于 `smoke/` 启动检查（4K 输入、8 输出），与正式结果严格分开。

## 场景、时钟与跨轮缓存

每个独立策略轨迹只在开始前 reset 一次缓存，以避免前一个策略污染。**轮次之间、
热点变化和扩容事件都不 reset**；路由状态和实物缓存均保留，自然驱逐也保留。
每次 reset 有事件记录，汇总要求每轨迹恰好一次。

AgentX 会话均使用相对零时间，没有真实全局会话启动时刻。因此以下是明确构造的
混合流量，不能称为恢复的生产集群到达过程：

- 均衡：128 个子流各请求一次，每轮到达均匀展开于 30 秒；三轮分别从 0/60/120 秒开始。
- 阶段热点：首轮相同，之后两轮集中到固定的 32 个子流，每流四次连续请求。热点身份在看到策略结果前固定。
- 突发：128 个子流分别在 0/60/120 秒同时到达一次。
- 扩容：采用均衡到达，初始两个活跃引擎，60 秒时逻辑加入第三个，缓存不清空。模型和通信已预热，不是含模型冷启动的物理扩容。

子流内维持前序请求完成依赖。原始 API 耗时/gap 作为溯源保存，不冒充本地服务时间；
这次受控到达实验不声称原始工具时间重放。固定到达压力下，小 BS 可能积累大量
客户端队列，这部分不会从延迟中扣除。

首 token 和完成延迟均从计划到达时刻起算，包括依赖等待、BS admission、router
等待、准备阻塞及引擎等待。另列各段时间。失败计入 SLO 分母；未产生首 token 的
请求在全流量尾部分位数中视为无穷，JSON 用 null 表示无有限分位数。

## 算法与状态准备

DualMap 使用本地干净的上游 commit `24816acc70b8e8f4f6b47bc47b7ce0fdddddf40d`，
保留真实队列、双哈希与再平衡逻辑。动态加入节点是本 harness 的成员变更适配，
保留已有副本元数据与在途回调身份，已单测。CacheRoute 使用仓库已有论文 Algorithm 1
实现，不是作者官方 artifact。其计划只用已到达的历史请求计数，不能读取未来评测请求。
32K/16 输出的独立校准用于路由成本/qcap；异质长输出的估计误差是明确限制。

所有策略使用相同的实际 snapshot 观测接口。DualMap 的混合模型可执行边界由引擎
观测修正，不能仅凭模拟 hash 命中就宣称 recurrent state 存在。真实缓存命中以生成
返回的 `cached_tokens` 为准，元数据观测开销计入端到端时间。

加迁移组使用现有 HybridMigrationCoordinator 和真实 RCCL 复制。准备触发器只看
已经到达的待处理请求、当前在途负载和已完成的源输入快照，不使用未来工具结束时间。
当前源端忙、目标忙、目标非空、容量不足、没有长快照、目标已有温热前缀等情况
分别统计跳过原因，**不暂停全局流量等待空闲，也不清目标缓存来制造可迁移条件**。
这是现有受限实现的比较，不是补齐后台搬运/非空导入后的理想上界。

加提前重算组使用相同负载触发和已完成输入快照；可在目标直接生成一个 token
物化状态。额外 prefill、阻塞和空间竞争均实际发生并计时。准备时其他可用引擎
继续服务。原生路由组没有这些额外计算。

源复制后缓存可能保留，因此同时报告物理 HBM 和 KV token/snapshot pool 占用，
不将 owner 改变等同于源端 HBM 回收。

## 指标与质量门槛

- 全流量首 token p50/p95/p99，完成延迟、平均 TPOT；按 phase 另列，观察自然预热后是否仍有增益。
- 选定子流的任务完成时间（末完成−首次计划到达），不是完整原始 agent 任务的语义完成时间。
- 主 SLO：TTFT≤10 秒、平均 TPOT≤0.2 秒。另保留 TTFT 1/5/10/30 秒 × TPOT 0.1/0.2/0.5 秒的敏感性结果。阈值是实验设定，不是生产 SLA。
- goodput 使用全部请求及全段时长，包含失败和准备尾部；同时报告 SLO 达标率。
- 真实迁移字节、准备次数/失败/跳过原因、准备耗时、HBM 使用、KV/snapshot 占用及实测 running/queued。

之前已发现该运行时对 batch 形状敏感，greedy 输出不一定逐 token 相同。本次保留
全部输出及 SHA，长度检查是实时门槛；goodput 是**长度有效的性能观测**，不能自动
解读为质量一致的 SLO goodput。跨策略语义/输出一致性必须另行审计，失败不能隐去。

## 运行状态与故障保留

初次预检在连续创建通信组时出现 TP 控制 collective 对象错配，节点退出。
原始失败留在 `results/campaign-20260928/`，不计入正式性能样本。
第二次尝试使用任务独立 overlay，为控制消息创建独立 Gloo group，并关闭未使用
的服务端 metrics 选项，但仍失败，记录留在 `results/campaign-20260928-r2/`。
随后定位到端口 33411 已有监听服务：一片 TCPStore 初始化失败，另一片却进入内部
gather，导致错误汇总失配。第三次改用逐节点逐端口 bind 检查过的 24100–24143
分组范围（每对起点间隔 8），并将 TCPStore/身份阶段的异常在 TP 内同步后返回。
请求负载和显存通过已有接口采集。每个定向通信组先检查真实传输及续写输出，再
检查路由器与扩容；失败不通过清缓存伪装成正式性能数据。

当前尝试目录为 `results/campaign-20260928-r3/`；`status.json` 和每项的
`heartbeat.json` 自动更新，完成项更新 `completed.json`、`PROGRESS.md`。
后台进程运行于 node27，日志为 `results/campaign-r3.log`。正式推理失败会保留记录并
停止后续矩阵，避免在损坏后端上产生无效排名。结束或失败时只停止本任务的三个容器。
