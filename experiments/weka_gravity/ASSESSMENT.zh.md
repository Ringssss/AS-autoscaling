**判断：研究问题有现实依据，值得继续；当前海光实现尚不具备解决持续多节点冷热不均的完整能力。**
这批 trace 能证明长历史和持续复用造成强缓存亲和，也能识别潜在搬运间隙。
它不能单独证明原生产集群存在多少负载倾斜，更不能直接推出迁移带来的吞吐提升。
应将系统目标定位为：在缓存亲和妨碍负载均衡、扩容或接管时，以受控代价改变状态位置。

## 审计边界与不能推断的事实

`audit.py` 按每个会话的请求开始/结束事件处理：只有已完成请求的输入块能
进入缓存，模型不同则隔离；所有 hash ID 始终限制在单个会话中。核对了所有
哈希的前驱一致性，未发现冲突；所有请求均满足 `in = 64 × hash_ids 数量`。
单元测试覆盖在途前缀不能提前命中、同会话子流共享、模型隔离、会话隔离及 TTL。

全部 393 个会话从相对时间零开始，没有跨会话绝对开始时间、原执行节点、
GPU 队列、真实 KV 容量和驱逐记录，也没有原始 token 文本/ID。不能把它们的
`t=0` 全部对齐后称为真实生产并发，也不能把本地 hash 0 当作跨会话公共模板。
`api_time` 是原始系统观测耗时，不能直接作为本地 Qwen/海光 GPU 的服务时间。
高复用本身也不能证明缓存仅驻留在一个节点：发布文件没有实际副本分布，无法
排除某些目标本来就温热。因此这里证明的是强局部性需求，不是已观测到单节点引力。

有 5,727 对同流/同模型相邻请求显著重叠，另有一个浮点精度级负间隙。
这些不纳入非负等待窗口。相邻请求也不等于数据集显式提供的因果父子边；
本文用相同前缀、同流、同模型和完成时间限定候选，避免凭空补造工具调用关系。

该数据集经过至少 20 次请求、版本、并发子 agent 上限等筛选，排除了部分异常
和图像请求。因此机会比例只适用于这批公开长会话语料，不能直接推广为生产流量占比。
观察到的未来间隙在离线分析中可用；在线控制器只能利用当时已经知道的信息。

## 迁移何时值得

设源/目标等待为 Qs/Qd、迁移时间为 M、可利用间隙为 G、温热续写成本为 W、
额外冷 prefill 成本为 P。忽略批处理相互影响的近似比较为：

- 原地：Qs + W。
- 冷改派：Qd + P + W。
- 提前迁移：Qd + max(0, M − G) + W，加上干扰和容量成本。

迁移同时需要胜过最好的不迁移选择。相对原地，决定因素是源/目标等待差是否
超过暴露迁移尾部及干扰；相对冷改派，决定因素是省下的重算是否超过这些成本。
目标已经温热、源没有拥塞、历史很短、窗口太短，或目标空间不足时，应不迁移。

还需要区分计算热点与显存热点：队列长时应改善后续计算放置；大量长时间不返回的
冷会话占据 HBM 时，移到另一个 GPU 可能只是转移压力，CPU/SSD 分层或驱逐再恢复
也应参与比较。间隙越长不代表越应占着另一份 GPU 状态。

**长 gap 也可能让目标提前重算完成。** 必须给予 precompute 相同的已知前缀和
相同的准备窗口，才能说明复制状态的额外价值。状态复制不是唯一改善局部性的方法。

实际 Claude 架构和状态布局不能从这些 hash ID 推导。`copy_window_sensitivity`
给出的是不同每 token 状态大小/有效带宽的条件估计，不是 Claude 的实测迁移时间。
本地混合模型实际约 20 KiB/token 加固定 recurrent/conv 状态；普通全注意力模型
可能不同。有效带宽还必须计入打包、RPC、HBM 读写和网络竞争，不能拿网卡峰值直接代入。

## 当前仓库最关键的实现缺口

1. **等待中的 agent 不等于空闲的 engine。**
   `experiments/hygon_runtime/hybrid_control.py:39` 要求整个 scheduler 空闲。
   热点 engine 正处理其他 agent 时，即使待迁 agent 处于工具阶段，也不能直接搬。
   `transfer()` 在 scheduler 内同步执行，并对每个 tensor 等待 collective 完成；
   这与持续负载下后台迁出有本质差别。
2. **目标必须是空缓存。**
   同文件 `transfer()` 检查 `root_node.children`。真实较冷节点通常已有其他会话，
   不应为接收一个 agent 清空全部缓存。需要非空 radix 导入、共享块去重、容量预留、
   驱逐与失败回滚，以及混合模型完整边界的安装。
3. **当前直接路径复制成功不等于释放源 HBM。**
   源的旧 KV/混合状态仍可留在缓存中。它可以改变后续计算位置，但不能直接声称
   解除了源端显存压力。需要区分 owner 转移、unpin、物理回收、短期影子和真退役。
4. **放置策略的成本和预测仍是原型。**
   `CostBenefitPlacementPolicy.score()` 对正 queue 差加入重算收益，而保留温热源
   本来不需要重算；评估应对比最佳不迁移方案，避免高估搬运收益。
   `GlobalMobilityPolicy` 使用 `active_requests + warm_states` 等启发式，尚没有本次
   workload 的在线队列/服务时间、窗口、共享链路拥塞估计。不能把事后知道的 gap
   或 future service 作为线上可用的事实。
5. **模型与状态范围必须匹配。**
   不同 Claude 模型不能互相搬 KV；本地 Qwen 的 recurrent/conv state 也不能仅凭
   KV 长度相同就视为可续写。当前 Hygon 混合模型只能导出完整可执行快照边界。
   trace 中完整保留前次输入，也不保证真实引擎恰好物化并保留了该输入边界快照。
6. **通信组和真实扩容成本。**
   需要管理 TP rendezvous 端口范围、组复用与清理；当前 coordinator 默认 pair
   port 相邻，而 TP2 每对使用四个端口。本轮三节点 harness 显式分隔端口。
   通信预热、模型加载和节点退出成本不能从 autoscaling 指标中消失。

以上针对当前可运行的海光路径。仓库其他异步/NVIDIA 实现不能自动视为这些节点
上已通过验证的功能。本轮不修改原有运行时代码，避免将机制评估混同于系统重写。

本轮三节点回流实验另发现严格输出一致性失败：同一份历史在 sticky 三请求 batch
和分布式执行时，greedy 输出出现差异。复制、冷改派和提前重算三者在分布式放置下
相互一致。该组时间只作诊断观测，不能用于宣称有效系统加速；保留原始输入和失败，
另做同节点、无迁移的 batch/serial 诊断。两条链路的串行迁移组件实验则全部通过。

## 该继续投入什么

优先验证 **受预算约束的状态迁移，是否在稳态缓存感知路由之上提供增益**。
第一阶段应补齐非空目标导入、繁忙 engine 中安全的后台复制、提交后可观测的源端
回收，并把迁移字节、复制对前台的影响和容量占用纳入 admission。

随后在 3–4 节点上进行持续到达的闭环比较：sticky、负载感知冷改派、缓存感知
路由、同一路由加 migration、同一路由加 precompute。所有策略保留跨轮缓存，
相同模型/TP/容量、相同请求、相同准备信息；不把候选过滤或输出截短隐藏在结果中。
需包含本来平衡、自然阶段性热点、突发、显存压力、扩容、源退出以及目标本已温热的反例。

报告全流量 TTFT/TPOT/p95/p99、任务完成时间、SLO goodput、每节点利用率和队列、
额外迁移流量、源端回收及失败。迁移频率和收益持续性应单独报告；一次冷目标接管
成功不能证明长期均衡。缺失的全局会话启动时间可以用多组明确标注的生成混合进行
敏感性分析，不能伪称恢复了原始生产拓扑。

**是否继续的标准：** 在上述强基线和完整成本下仍降低尾延迟、提升 SLO goodput，
且改善能在多轮缓存自然预热后持续，才支持完整系统主张。如果增益仅在目标初始
全冷的第一次出现，应收缩为冷扩容/节点排空/故障接管的状态准备机制。

本轮实际硬件测量另见 `MEASUREMENTS.zh.md`，其中严格区分新测量、原始 trace
统计和受控负载。详细机器清单、代码摘要及原始记录保存在 `results/`。
