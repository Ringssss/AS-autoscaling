# 海光跨节点实测结果（2026-09-22）

**已验证长前缀发生冷改派时，迁移状态能显著减少首 token 等待；尚未证明
AS-autoscaling 在 4 节点 32 卡生产流量上整体优于 DualMap 或 CacheRoute。**

本轮部署为 **3 节点、6 张卡、3 个 TP2 引擎**，两条链路分别顺序测量。
node30 的八张卡和 node28 的部分卡被既有任务占用，未停止这些任务。
本轮使用空闲卡，但整机 CPU/网络不是独占实验环境。

## 1. 已完成的真实测量

相同的 Qwen3.6-35B-A3B BF16 模型、相同运行时、131072 上下文，使用
LongBench 的真实政府报告文本填充。父输入产生一个 token 以固化输入边界，
子输入延长 32 个给定 token，再生成 16 个 token。这是已知前缀的组件实验，
不是恢复了 Kimi 原始对话，也不是完整 agent/tool 工作流。

每个前缀、每种模式、每条链路重复 3 次，随机化模式与长度顺序。下表为
**首 token 延迟中位数，单位毫秒**；比值为冷改派中位数 / 迁移中位数。
迁移列包括 RPC、真实状态复制、目标就绪、SQLite 所有权提交与目标推理。
没有扣除假想 tool gap，也没有假定迁移可以免费隐藏。

| 链路与网络配置 | 前缀 token | 冷目标改派 ms | 返回时迁移 ms | 已温热目标改派 ms | 冷改派/迁移 |
|---|---:|---:|---:|---:|---:|
| node27→node28（自动选卡） | 1,024 | 313.3 | 332.1 | 301.3 | 0.94× |
| node27→node28（自动选卡） | 8,192 | 902.2 | 365.0 | 312.2 | 2.47× |
| node27→node28（自动选卡） | 32,768 | 3175.6 | 478.3 | 349.8 | 6.64× |
| node27→node29（固定 shca_0） | 1,024 | 317.8 | 335.3 | 309.8 | 0.95× |
| node27→node29（固定 shca_0） | 8,192 | 905.8 | 363.6 | 322.0 | 2.49× |
| node27→node29（固定 shca_0） | 32,768 | 3175.6 | 477.6 | 355.3 | 6.65× |

- 两条链路合计 **72 个正式续写请求全部通过**：逐 token 输出与 sticky/cold
  对照一致，输入/输出长度准确，实际缓存命中符合预期，迁移所有权已提交。
- 每条链路有 9 次正式迁移和 1 次通信预热迁移，持久化记录均为 `COMMITTED`。
- 1K、8K、32K 实际传输量分别为 **85,360,640、232,161,280、735,477,760 bytes**，
  是两个 TP 分片的总和，包含完整注意力 KV、卷积状态和 FP32 recurrent state。
- 两个目的地各自的冷/热对照表明，丢失这段前缀的增量 TTFT 约为：1K
  **8–12 ms**，8K **584–590 ms**，32K **2820–2826 ms**。
- **1K 是反例**：迁移比冷改派约慢 5.5%–6.0%。目标已经温热时，直接路由也
  比先复制状态更快。因此“每次 A→B 都值得迁移”不成立。

这些改善是相对于**已知冷目标改派**，不是相对于 DualMap 或 CacheRoute
完整路由策略的改善。两个策略可能保留亲和，或选择已经温热的目标；实际
策略结果还取决于这些事件的频率、排队、驱逐、拥塞和副本负载。

### 初始化成本没有隐藏

上表是**通信组和内核已预热后的稳态组件成本**。两次正式 campaign 的
通信组创建分别另耗时 **21.78 s、26.99 s**，第一次真实传输预热分别为
**0.373 s、0.340 s**，原始记录均保留。新目标/新通信组出现时，必须计入
这些成本，或实证它们在请求到来之前完成。当前结果不能直接用于声称
首次迁移或冷扩容也有上述加速。

没有注入前台争用，没有测全流量 p99、SLO 容量、goodput 或物理 GPU
退役。每格只有 3 次，报告中位数/原始范围，不把相关请求当作大样本置信区间。

## 2. 网络与失败记录

- 四台机器各有 8 张 64 GiB 海光 BW 卡、4 个 Active 的 400 Gb/s IB 端口。
- 主机 RDMA_Write：node28→node27，单端口、8 MiB 消息、5 秒窗口，平均
  **220.38 Gb/s**。另一条跨 HCA 的 node29→node27 主机测试约 **132.41 Gb/s**。
  这是具体探针的结果，不是“四端口峰值带宽”的宣称。
- 镜像需要 `NCCL_NET_PLUGIN=shca` 与 `NCCL_NET=IBext_v8`，并暴露
  `/dev/infiniband`。实测模型迁移日志包含 `NET/IBext_v8` 数据通道。
- node27→node29 的自动 HCA 配置在**首次传输预热**中发生 RCCL broadcast
  90 秒超时；这轮未产生正式测量样本，记录为失败，控制器 ledger 为 `ABORTED`。
- 固定 `shca_0` 的独立跨节点 GPU 探针通过了全部数据校验，256 MiB 的
  四次接收侧用时为约 **9.82–9.90 ms**。固定 HCA 并重启后的完整模型重复
  实验也通过。没有单独隔离网卡选择与重启的影响，不能断言唯一根因。
- 两条成功链路的网卡设置不同，已分别标注；没有混成同配置跨节点吞吐均值。

- **8,455** 条 `cached_tokens > input_length`；这些记录均只有 1 个输入和 1 个

- 输入长度 p50/p90/p99 为 **8,090 / 38,738 / 102,749**；输出长度为
  **350 / 1,665 / 7,233**。到达时间跨度约 **24.97 小时**。
- 4K 上下文只容纳约 **6.73%** 的原始输入+输出长度，64K 容纳约 **95.48%**，
  当前 128K 上下文容纳 **100%**。本轮组件网格不等同于全 trace 重放。

`cached_tokens` 只描述历史执行处的计数，不提供另一个目标是否持有同一前缀
的信息。相同统计既可能来自每台机器都温热的全局模板，也可能来自只在源端
驻留的会话前缀，两者的 routing tax 完全不同。当前发布数据无法区分它们。

用 ToolBench/ShareGPT/LongBench 补内容可以做“生产时间/长度驱动的重建
工作负载”，但不能把补造的会话键、前缀复用关系和工具间隔称为原始生产事实。
要做原生的 cache-aware policy 排名，需要稳定匿名 session/business key、
精确前缀/块哈希与父子关联；要声称 tool-gap overlap，还需要真实工具边界时间。

## 5. 完整 32 卡结论仍需要什么

1. 32 卡可用的实验窗口；当前 node30 全部卡和 node28 部分卡仍有既有任务。
2. 明确选择“原生前缀身份 trace”或“明确标注重建复用关系的 trace-shaped
   workload”。当前发布版本无法推出原生缓存策略排名。
3. 当前 Hygon 迁移原型仍限制空闲引擎、空目标缓存，尚需非空缓存导入、
   并发 admission/eviction、通信组清理和跨主机/双向/TP 端口管理。不能为让
   AgentShift 工作而清空其他策略的真实目标缓存。
4. 按 [PROTOCOL.md](PROTOCOL.md) 做同配置、同负载、含失败和反例的成对
   多轮稳态/突发/扩缩容实验，再比较真实 p99、SLO goodput 和资源成本。

当前证据支持的是：**长前缀确实因改派而变冷时，状态迁移有明显收益空间；
不能据此断言在真实 4×8 集群上全面优于两个缓存感知路由算法。**
