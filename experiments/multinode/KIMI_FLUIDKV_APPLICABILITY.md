# Kimi production trace：FluidKV 的适用覆盖与证据边界

分析日期：2026-09-23。结论：**长输入和延迟尾部确实存在；长缓存候选请求每小时都出现，但不是主流。此 release 无法识别必须迁移、可提前搬运的事件频率，不能证明生产上 FluidKV 明显胜过 routing。**

## 数据与核验

全量归档 SHA-256：`e7d8fd50757208220b9bc5bbd111a9d491b94a89a6c42390ab345aab9a0c3513`。
24 个 finish 日志、245,555 个唯一请求，所记录请求的 arrival 跨度约 24.97 小时。
本次重新流式读取归档，校验逐文件摘要，并对照此前规范化文件逐行检查。
这是一份已完成请求的生产观测，不能据此推断整个生产集群所有流量、利用率或所有 agent 产品。

全部输入/输出 token ID 脱敏；conversation_id、routing_key、extra_key、session_params、bootstrap_pair_key 均没有非空值。
8,455 条记录的 cached_tokens 大于 input_length（这些记录 input/output 都为 1），排除出缓存统计，未自行修复。表中覆盖率分母仍为全部 245,555 条请求。

## 哪些条件常见

K=1024 tokens；“已记录缓存”是历史执行路径上的 cached_tokens，不代表私有历史、可导出的状态、其他副本冷缓存或必须迁移。

| 阈值 | 输入达到阈值 | 已记录缓存达到阈值 | 长缓存请求数 | 长缓存人群占累计 TTFT |
|---|---:|---:|---:|---:|
| 8K | 49.57% | 5.82% | 14,301 | 9.97% |
| 16K | 29.28% | 3.50% | 8,599 | 6.57% |
| 32K | 12.52% | 1.77% | 4,357 | 3.94% |
| 64K | 4.30% | 0.58% | 1,435 | 1.58% |

81.23% 的全部请求记录到 5,440–5,888 tokens 缓存。这与大量请求只复用较短前缀相容，但缺少前缀身份，不能断定它们共享同一系统提示。
≥64K 输入人群的已记录缓存/输入比例中位数仅约 **7.00%**，不能把这批长输入直接用于“64K 状态搬运”的覆盖率论证。
有效缓存记录的 token 加权命中率为 40.71%，也不能解释为 40.71% 请求有迁移收益。

相对首次 arrival 的前 24 个完整小时中，≥32K 长缓存每小时 36–549 条（中位数 106）；≥64K 每小时 11–174 条（中位数 31.5）。后者每小时请求占比 0.12%–1.73%。因此候选人群反复出现，但“候选存在”不等于“每小时确有这么多接管”。末尾不完整小时未纳入小时范围。

## 延迟压力是否明显

全体 TTFT p50=1.12 秒、p95=19.35 秒、p99=41.50 秒。≥64K 输入的 TTFT p50=9.18 秒，长输入确实对应更大的延迟负担，但没有完成因果分解。

按每分钟到达数分组，高到达量分钟的 TTFT p95 为 28.44 秒，低到达量分钟为 10.47 秒。高到达量组的 ≥32K 长缓存占比为 2.23%，低到达量组为 2.78%；不能据此声称繁忙时段的大多数慢请求都是长状态位置错配。到达量并非 GPU 利用率，输入组成也随时段改变。

25,710 条请求 TTFT ≥10 秒，其中仅 1,136 条（4.42%）具有 ≥32K 已记录缓存，512 条（1.99%）具有 ≥64K 已记录缓存。**现有数据不能把主要延迟尾部归因于长缓存迁移问题。** 缓存少也可能源于其他位置存在状态但未命中；这需要全局驻留日志验证。

## 7–10 倍事件收益如何折算到整体

下面是条件化的算术敏感性分析，**不是 FluidKV 实测，也不是生产收益预测**。假设只改变某一已观测长缓存人群的 TTFT，其余请求、decode 和排队反馈都固定。

极端地把该人群的全部 TTFT 消除：

| 被改变的人群 | 全体平均 TTFT 加速 | 全体平均请求完成延迟加速 |
|---|---:|---:|
| 已记录缓存 ≥8K | 1.111× | 1.024× |
| 已记录缓存 ≥32K | 1.041× | 1.009× |
| 已记录缓存 ≥64K | 1.016× | 1.004× |

这些仅为“只改变该人群”的条件化极限，不是 FluidKV 的全局上界：迁移可能帮助别的人群、减少其他请求排队，也可能争用网络和显存。

令 b 为人群占全体累计 TTFT 的比例，q 为其中受影响的 TTFT 总量比例，s 为该部分 TTFT 加速，则整体平均 TTFT 加速为 `1 / (1 - b*q*(1-1/s))`。q 不是日志测得的迁移概率；只有受影响请求具有代表性时才可近似看成请求比例。
例如所有 ≥64K 长缓存请求都获得 7 倍局部 TTFT 加速，整体平均 TTFT 也仅约 1.014×。局部事件大倍率与全量均值大倍率是不同主张。不得把此公式用于推算吞吐或 p95。

## 方法何时奏效，这份 trace 能证明什么

需要同时满足：

1. 温热执行位置不可用或等待成本较高，例如计划退出、会话重分配、负载失衡。
2. 有可复用且可迁移的历史状态，目标缺少该状态，并有可用资源。
3. 搬运和干扰成本小于重算或留在源端等待；工具窗口可进一步隐藏搬运。

若搬运 C、重算 R、可用准备窗口 W，则最有辨识度的窗口为 `C ≤ W < R`。此前 Qwen3.6 六卡实验的 C≈0.485 秒、R≈7.25 秒、W=0.5 秒证明了这一机制；**这些成本不能直接移植到 Kimi K2.5 的模型、硬件和缓存格式上**。

本 trace 缺少工具起止、因果 turn/session 身份、前缀/block 身份、实际引擎级缓存驻留与副本成员变更。请求到达间隔不能替代工具窗口，bootstrap_host 或 dp_rank 变化不能直接解释为热源退出。queue_time 全为零也不足以证明没有排队。

因此，收益窗口 `C ≤ W < R` 的覆盖率和“温热源不可选”的频率均不可识别。此数据同样允许“热源一直可用，纯 routing 已足够”和“其他位置有状态，但路由未命中”这两种解释。

定位建议：当前最有证据的是**长状态在副本切换时的接管加速**。这份生产样本支持候选状态规模并非虚构，但不支持把“持续多倍全站加速”作为已经验证的卖点，也不能评价“简单 routing + FluidKV”是否胜过单独 DualMap/CacheRoute。

下一步应补采保留隐私的 session/turn ID、prefix/block hash、tool ready 时间、每个引擎的驻留/驱逐与成员事件，并标定实际后端的搬运/重算成本。用这些字段直接统计三条件的交集，再对该交集做配对实测；现有空闲源、空目标的实现限制也需要纳入可执行覆盖率。
