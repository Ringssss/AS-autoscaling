# 工具阶段迁移与热点副本：实测补充

本轮完成了 **node27→node29、两节点四卡 TP2** 的工具窗口机制实验。
**尚未完成四节点实验**：node30 八张 64 GiB 卡仍各占用约 53 GB，
启动器拒绝与现有工作负载共用，四节点健康门槛也在 node30 处失败。
同一镜像已下载至 node30（image ID 与现有引擎一致），启动配置和
四节点顺序测试入口已准备好。需要先安排两张空闲卡；四节点一副本/节点
是八卡，不是 32 卡全量实验。

## 实验回答的具体问题

在固定源/目标、给定已完成输入快照的条件下，工具窗口前段复制状态，
是否能改善工具返回后遇到源端负载时的续写？

三个机制对照是：留在温热源端、直接路由到冷空闲目标、工具阶段复制后
在目标续写。所有方案在工具开始后 200 ms 向源端提交同一个 64-token
前台生成请求；源端使用正常连续批处理，没有人为添加串行队列。

真实本地仓库检索子进程产生实际工具结果，附加到同一 LongBench 文档
前缀后续写 16 tokens。50/500 ms 是**受控最小工具窗口**，不是从 Kimi
测得的生产工具时长。快照由 one-token 生成固化输入边界，未声称复现
模型自主发起工具调用的完整 agent 工作流。

## 预热后结果

1K/32K × 50/500 ms × 三种机制 × 三次重复，共 **36 次正式续写全部通过**。
检查包括与 sticky/cold 的逐 token 输出一致、真实缓存命中、输入/输出及
前台生成长度、传输字节数、所有权提交，以及客户端时间线的因果顺序。
12 次正式迁移和 1 次通信预热迁移的 SQLite 记录均为 `COMMITTED`。

下表是工具返回到首 token 的**中位数，单位 ms**；统计单位每格 3 次。

| 前缀 tokens | 控制工具窗口 ms | 留在源端 | 冷目标路由 | 工具阶段复制 | 复制暴露尾部 ms |
|---|---:|---:|---:|---:|---:|
| 1,024 | 50 | 368.4 | 321.3 | 318.5 | 0.0 |
| 1,024 | 500 | 351.4 | 322.6 | 318.8 | 0.0 |
| 32,768 | 50 | 430.3 | 3193.1 | 434.8 | 64.5 |
| 32,768 | 500 | 500.8 | 3196.2 | 371.7 | 0.0 |

500 ms 窗口下，全部试验在工具返回时都有源端前台请求尚未完成。
50 ms 窗口下，前台请求尚未到达，因此这组不是“工具返回时源端过热”的
证据；它检验短窗口和随后到来的负载。实际工具计算耗时、返回时刻、
前台到达/首 token/结束、复制开始/提交、续写各时间点全部保存在原始记录。

### 32K / 500 ms 的收益与外部代价

- TTFT：501 → 372 ms，相对留在源端约 **1.35×**；冷路由 3196 → 372 ms，
  约 **8.60×**。后一个比值是相对强制冷目标控制，不是相对 DualMap/CacheRoute。
- 16-token 续写完成时间：源端 **2.539 s**、冷路由 **5.175 s**、迁移 **2.352 s**。
  完成时间的收益小于首 token 收益，不能把 TTFT 比值称为全任务加速。
- 前台请求到达至完成中位数：源端续写 **9.058 s**、冷目标路由 **8.816 s**、
  工具阶段复制 **8.898 s**。复制相对冷路由约增加 **82 ms（约 0.9%）**，
  相对源端续写约减少 **160 ms**。这些是少量观测，不足以断言总体干扰为零
  或精确归因其差值；原始成对数据与范围已保留。
- 32K / 50 ms：复制暴露约 **65 ms**，首 token 435 ms 对源端 430 ms，
  没有显示优势；1K 下冷路由与复制仅差约数 ms，不宣称显著收益。

### 初始化、预热与限定条件

主结果的通信组初始化耗时 **21.999 s**，
首次复制预热 **0.402 s**，另行记录，不在稳态请求表中。
新建副本或未初始化的迁移目标不能直接套用稳态结果。
串行与并发执行形状均提前预热，RCCL 首次传输也预热。
之前一轮只有串行预热、首个 sticky 请求偏慢，已保留为探索数据，不用于主表。

当前实现是同步复制、源端须空闲、目标缓存须为空；源端 foreground 在
工具开始 200 ms 后才到达。实验支持“提前迁移，避开返回时的源端负载”，
没有验证“源端当前已满载时仍可无干扰迁出”。没有动态选择目标、生产复用
键、并发多 agent 回流、缓存压力或整机独占；尚不能宣称副本负载方差、
全局 p99、goodput、吞吐或 32 卡扩缩容改善。源端旧缓存仍可能保留，
复制成功也不等于源端内存已释放或物理 GPU 已退役。

## FluidKV 的核心 insight

1. **负载热度和缓存热度不是同一件事。** Routing 可以把请求送到较空闲
   的副本，但目标可能缺少 agent 的完整可续写状态。FluidKV 提供主动
   改变状态位置的能力，把“空闲但冷”的副本变成这个 agent 的温热候选。
   如果 router 已经能选到空闲且温热的目标，直接路由就很好，没必要复制。
2. **工具等待是带截止时间的准备窗口。** 已完成前缀不依赖未来工具结果，
   可以先搬；工具结果作为后缀在返回后处理。窗口足够长时复制可从返回
   路径移走，窗口过短则仍需付出复制尾部。这次反例表明窗口必须进入决策。
3. **可避免的是“为负载均衡付出的局部性损失”。** Routing 把计算移向已有
   状态，FluidKV 还能把状态移向未来的计算位置。它能放松亲和与负载之间
   的冲突，但复制带宽、空间、双份状态和对前台请求的干扰都是成本。
4. **更合理的是条件式叠加，不是无条件替代 routing。** 保留 DualMap /
   CacheRoute 的温热亲和选择，在剩余工具窗口、源/目标预计负载、重算成本
   与复制成本都支持时才准备新目标。应比较同一 router 有/无状态准备的
   ablation，再与两个原算法做全流量比较。这次没有运行两个算法的策略排名。

简化决策式（仅帮助解释，实际排队/批处理会相互影响）：

- 原地：源端等待/干扰 + 温热续写；
- 冷路由：目标等待 + 冷重算 + 续写；
- 工具阶段复制：max(0, 准备时间 − 剩余工具时间) + 目标等待 + 温热续写。

还要加入复制对其他请求、网络和内存容量的代价。完整状态含 KV、卷积与
recurrent state；单有同长度 KV 匹配不代表这个混合模型可正确续写。
