## 0. 一句话论点

> **Agentic 负载的状态局部性把请求放置钉在缓存位置上。路由只能转移计算：
> 贴亲和则热引擎排队，做均衡则每条请求付全额状态重建——实测 p50 差 4.2×、
> goodput 差 3.2×。FluidKV 把"可运行前缀"变成可搬运的对象：
> 在完整边界上搬运成套状态（`C ≈ 0.2–0.6s` vs `R ≈ 19–28s`），
> 并用资源可行性闸门决定何时值得这么做。**

中心贡献：**把一次昂贵的冷分流，转化为有选择、有预算、可验证的状态交接。**
副贡献（本轮确立）：**状态迁移的系统瓶颈不是传输带宽，而是通信组的生命周期
管理**——group 必须每对建立一次并复用，重建不可重试且会级联污染引擎。

### 0.1 措辞纪律（本轮新增，违反即为过度声称）

| 不能写 | 只能写 |
|---|---|
| 路由方法"不够好" | 路由**无法转移状态**，因此均衡必须付 `R(n)` |
| 我们比路由快 | 我们让**均衡不再需要**付状态重建的代价 |
| 常态负载均衡 | scale-out / 新 worker 预热 / **冷引擎**接纳 |
| 每对需迁 ≥1.83 次才回本 | **一次迁移即回本**（init 0.06–0.16s，已修正） |
| `init_once ≈ 16–31s` | **已被推翻**，见 §3.6/§3.8 |

## 1. 论证链（每一步都可证伪）

```
[E1] agentic 负载冷热极度不均
     └ 少数超长前缀承载多数复用价值；相当比例的请求本质无前缀可复用
       证伪条件：trace 里复用分布不是重尾 / 冷请求比例接近 0
       证据：rawcensus.json  98,827 请求 2,535 stream
             session p50=16 p99=475；最长 1% stream 承载 22.0% 请求，
             最长 10% 承载 59.0%；相邻请求 96.7% 有前缀复用
             ↓
[E2] 现有系统都是 routing algorithm，且命中是二元事件
     └ 请求→引擎的指派是唯一自由度；4K 命中与 130K 命中在目标函数里同值
       证伪条件：已有工作按前缀长度定价
       证据：代码核对（Preble 已按复用 token 数调度并把驱逐重算计入 load cost，
             CacheRoute 已有等大小 slot 预算）→ 因此不能说"都不看长度/容量"，
             只能说不区分"这次搬运的可行性"
             ↓
[E3] 均衡要求放弃亲和，代价随前缀长度增长，且与价值反相关
     └ 4K 弃之代价 ~0.5s，130K 弃之代价 ~28.2s
       证伪条件：长前缀的重算代价不随长度增长
       证据：sweep A/B/E + prefill 阶梯（本文件 §3）
             ↓
[E4] 搬运的成本远低于重建，且不随长度线性增长
     └ 这是 mobility 存在的物理理由
       证伪条件：传输耗时随长度线性增长，或跨节点显著劣于同节点
       证据：sweep A/B/D/E，95/96 格双向验证通过
             ⚠ 已测的是 **transfer 相位**，不含 group init，也不含目标侧
               服务首 token；所有交换比是空载下界。
       **group init 实测（2026-09-30，同节点对，5 次裸建链）：**
         16.3s / 21.1s / 21.2s / 21.5s / 31.3s，5/5 成功
       ❌ **上述 16–31s 已被 2026-10-01 的受控测量推翻。** 见 §3.6：
         健康引擎上 init 是 **0.06–0.16s**；16–31s 是**已降级引擎**上的
         数字，其成因是 process group 泄漏（`self.groups` 只增不减，
         group 永不销毁）。**不得再引用 16–31s 作为 init 成本。**
       **但它是每对一次的固定成本，不是每次迁移都付：**
         一次 init 15.66s 后，同一 group 上连续三次迁移
         0.62s / 0.12s / 0.12s，三次 `dst_verified=True`。
         协调器 `_ensure_group` 按 pair 短路（`self._groups[pair]`），
         与实测一致。**2026-10-01 复核：健康引擎上一个 group 连续
         12 次迁移全部成功，0.19–0.62s，引擎始终存活**（§3.6）。
       ⇒ **成本模型（已修订）：**
         `C_ready = init_once(pair) + k · per_transfer`
         `init_once ≈ 0.06–0.16s`（每对一次），`per_transfer ≈ 0.19–0.62s`。
         **一次迁移即可回本**（对比 `R(130K) ≈ 19–28s`，交换比 ~30–90×）。
         旧版"每对需迁 ≥1.83 次才回本"的结论**随之作废**。
             ↓
[E5] 但"可运行"不等于"token 匹配"
     └ 混合模型上，KV 之外还有 recurrent snapshot；边界不对齐的前缀不能解码
       证伪条件：KV-only 导入后目标仍能续写
       证据：KV-only 负控（待补）
       **实测确立的快照粒度（2026-09-30）：**
         32,768-token 前缀 → `snapshot_boundaries` 有 **8** 条
           [4096, 8192, 12288, 16384, 20480, 24576, 28672, 32768]
         130,048-token 前缀 → **32** 条（每 4096 一条）
         `FLA_CHUNK_SIZE = 64`，但快照粒度是 **4096**，即等于
         `chunked_prefill-size`，不是 FLA chunk。
       ⇒ 可迁移边界只能落在 4096 的倍数上；token LCP 与可运行边界
         最多差一个 chunk（4095 token）。这是"token 匹配 ≠ 可运行"的
         具体量化形式，可直接进论文。
       ⚠ **未决的异常：** 导入路径写入的节点，其边界条数尚未与 native
         写入的 32 条对比（`bounds-compare`，运行中）。若导入侧显著更少，
         则"导入后首个消费者不复用"（E7）的根因即为此。
             ↓
[E6] 容量是绑定资源，且未命中会驱逐一个等长的驻留前缀
     └ 2×2 配对实测（单引擎、引擎角色跨 rep 轮换、7 个驻留前缀）
       证伪条件：配对实验里命中的存活数不低于未命中
       **实测结果（P0-1，2026-09-30，4 reps/格）：**
         empty/miss 3.008s   empty/hit 0.623s
         full/hit   0.623s   full/miss 3.003s
         full/hit 存活 7/7（4/4 次、每一格完全一致）
         full/miss 存活 6/7（4/4 次，掉的是同一个 slot 0）
         `num_retractions` 恒为 0 → 该字段是**单请求被退回等待队列的次数**，
         不是缓存驱逐计数（源码 `io_struct.py` 注释已确认）
       ⚠ **被推翻的旧论断：** "仅内存压力就使 prefill 膨胀 2.4×（3.96s→9.54s）"。
         empty/miss 与 full/miss 在配对设计下**无可测差异**（3.008 vs 3.003）。
         旧数字来自三个不同引擎、不同 token 区域、且 free 在请求前后错时比较，
         是未配对设计的产物，**不得再引用**。
       ✅ **站得住的论断：** 满载下未命中的准入会驱逐**恰好一个**等长驻留前缀
         （28672 槽 = 32768 − 4096），而命中不驱逐任何前缀。
         这是"容量是被绑定资源"的直接证据。
       ✅ **长度扫描 @ 固定占用率（2026-10-01，`results/p05-length-sweep.json`）：**
         每个 L 装载 `(262144//L) − 1` 个驻留前缀，恰好留一个 L 请求的余量；
         hit 与 miss 起始占用**完全相同**；**miss 臂也逐对象数存活者**（旧脚本只数 hit）。
         | L | cold | hit | miss | hit/cold | 存活 hit / miss |
         |---|---|---|---|---|---|
         | 16,384 | 1.41 | **0.51** | 1.40 | 0.36× | 15/15 / **14/15** |
         | 32,768 | 2.99 | **0.62** | 2.99 | 0.21× | 7/7 / **6/7** |
         | 65,536 | 7.17 | **0.85** | 7.17 | 0.12× | 3/3 / **2/3** |
         三条结论：
         1. **`miss ≈ cold` 在每个长度上几乎精确相等**（1.40/1.41、2.99/2.99、7.17/7.17）
            → **"内存压力惩罚"在配对设计下再次不复现**，2.4× 确认死亡。
            所以 §2.3 的推论 (iii) 必须删除，只保留 (i)(ii)。
         2. **hit/cold 比值随长度单调下降（0.36→0.21→0.12），没有交叉点。**
            即"驻留是否划算"**不由时间决定，而由容量决定**——
            长前缀的驻留收益更大，但占用也更大。这是把动机从"时间轴"引向
            "容量轴"的定量依据。
         3. **未命中恰好驱逐 1 个等长邻居**，在三个长度上一致（15→14、7→6、3→2）。
            这是"驱逐一个等长前缀"论断的跨长度复现。
             ↓
[E7] 所以动作选择必须比较三个同终点的选项
     └ stay（原地服务）/ cold（目标重算）/ import（搬运后服务）
       证伪条件：始终按长度择优选，端到端不劣
       证据：P0-2 配对 E2E + 隔离复现
       ❌ **实测否定了 import 的服务收益（2026-09-30）。**
         同一终点、同引擎、同 130,048 token 前缀：
           cold   （目标重算）  median 19.540s  n=2
           local  （源已驻留）  median  1.402s  n=2
           import （搬运后服务）median 19.394s  n=2   dst_verified 双 True
           cold/import = **1.01×**  —— 搬运没有带来任何加速。
         隔离复现（28:31751 → 29:31761，避开一切并发实验）：
           转移 0.59s、bytes 2,727,772,160、state COMPLETE（两端一致）
           转移后立刻 inspect：`matched=130048, full=True, mamba=True` ← 已发布
           在该目标上服务该前缀：**79.40s，`cached_tokens=0`**
         ⇒ 状态被成功搬运并可见，但**首个消费者不复用它**。
       ⚠ **但这不是永久失效，而是"首个消费者惩罚"。** 32K 上实测：
           import 后 `serve#1 = 9.47s, cached=0`
                    `serve#2 = 0.38s, cached=32704`
         即第二次请求起复用正常。引擎侧日志独立确认：
           130K 目标 `#cached-token` 序列 0,…,0 → 126976 → 129984
           32K  目标 `#cached-token` 序列 0,…,0 → 32704
       ✅ 仪器有效性对照（同 build、同引擎、同一 run 内）：
          本地冷服务 `cached_tokens=0`；本地温服务 `cached_tokens=28672`。
          所以 `cached_tokens` 确实反映真实复用，
          "导入后首次 `cached_tokens=0`" **是真阴性，不是计数器失效**。
       ⚠ 结论对论文的影响：**在修复前，import 没有服务收益。**
       ✅ **修复已实施并验证（2026-09-30）。** 把导入改成按源端
         `snapshot_boundaries` 写**链式节点**（`hygon_hybrid_control.py`
         四处改动：新增 `boundary_values()`、源端枚举全部边界并 `torch.cat`
         成 K 槽 + 发布计划、目标端一次 `alloc(K)`、insert 循环 N 次并设
         `prev_prefix_len` 抑制内部释放、失败时 `tree_cache.reset()`）。
         32K 验证（`27:31791 → 28:31791`，跨节点）：
           **A. 导入树边界数 1 → 8**（= native 的 8）
           **B. 首个消费者 `cached_tokens` 0 → 28672**
           **B'. 首次服务 3.262s → 0.361s（7.4×）**
         ⇒ **之前的"无收益"是实现缺陷，不是机制限制。**
       ⚠ **C（跨引擎输出一致）不作为损坏证据**：同引擎连服三次输出
         各不相同（未打补丁的 `29:31761` 上同样成立），本 build 已知对
         batch 形状敏感。正确性要用同引擎对照，不能用跨引擎比对。

       ✅ **根因已定位（2026-09-30，五处代码证据 + 实测对照）：**
         请求路径把匹配键截掉最后一个 token：
           `max_prefix_len = input_len - 1`
           （`schedule_batch.py:1028`，注释写明 "to enable logprob computation"）
         而导入只写**一个节点**，快照仅挂末端：
           `snapshot_boundaries = 1`（实测 `[130048]`）
         对照 native 写入的是**边界链**：
           `snapshot_boundaries = 33`（31 个 4096 网格点 + `129984` + `130048`；
           早期记录写"32 条"是因为漏掉了 64 对齐点 `129984 = n − 64`）
         键短 1 token → 与单节点不精确对齐 → 触发
           `_split_node`，而其中明确写着
           `new_node.mamba_value = None  # mamba cache can not be split`
           （`mamba_radix_cache.py:1085`）
         → `best_value_len = 0` → `device_indices` 为空 → 全量 prefill。
       ✅ **关键对照证明"字节搬运无误，错的是树的形状"：**
         native 与 imported 的 `state_sha256` **完全相同**
         （`dc930ce8…`，2,727,772,160 bytes），
         但边界条数 32 vs 1。
       ⇒ 修复方向明确：导入端按 `snapshot_boundaries` 写**链式节点**，
         而不是单节点。当前 `transfer()` 只取
         `last_device_node.mamba_value` 一个槽
         （`hygon_hybrid_control.py:179`，目标端 `mamba_pool.alloc(1)`），
         需改为按边界数分配。
             ↓
[E8] FluidKV：可运行状态搬运 + 资源可行性闸门
     └ 三个组件，见 §4
       ✅ **搬运机制已端到端验证（修复后，130,048 token）：**
         导入树边界数 1 → **33**（= native）；
         首个消费者 `cached_tokens` 0 → **129984**；
         同终点三动作：cold 19.258s / import **0.591s** / local 0.594s。
         **cold/import ≈ 32.6×**（修复前 1.01×）。
         ⇒ E7 的负面结论已解除：mobility 在修好树形后确实有效。
       ⚠ **但仍未闭合的一项：** 全流量 SLO 收益（P0-3，同 router ± 真 copy）
         尚未跑；且 eligibility 只有 **5.6%**（65/1152），
         net-of-init 在 6 引擎拓扑上需每对迁移 ≥1.83 次才转正。
         **所以"机制有效"与"系统收益"是两件事，论文必须分开写。**
```

## 2. 实验矩阵

### P0（承重，改变论文结论）

| ID | 实验 | 回答什么 | 设计 | 停止条件 |
|---|---|---|---|---|
| **P0-1** | 容量配对 2×2 | 满载下未命中是否造成驱逐与邻居损失 | 同一引擎、引擎角色跨 rep 轮换；occupancy{empty,full} × residency{hit,miss} 四格；两臂驻留前缀数相同（起始空闲槽一致）；请求前后逐对象 `inspect` + 读引擎 `num_retractions` | 若四格无显著差异 → 删除 capacity cascade 的故事，只保留"容量可精确核算" |
| **P0-2** | 完整 import-to-first-token | 搬运到首 token 是否真的快于冷重算 | 同 pair 同 tokens：cold TTFT / local warm TTFT / import→首 token；三段计时 init/ready/resume | 先测 130K 单点；不通过就不扩长度矩阵 |
| **P0-3** | 同 router ± 真实 copy 的配对 E2E | 机制优势能否变成服务收益 | 同一 router、同 GPU 预算、同 warmup、同 arrival；treatment 是**真实 RCCL copy**（不是 reroute）；全流量计入 | 无净收益 → 收窄为机制论文，如实写 |

> **P0-3 的关键修正：** 现有 `real_compare.py` 里名为 `dualmap`/`+move` 的策略是
> 两选择哈希启发式与**重路由**，不是状态拷贝。它们只能作为 affinity 消融，
> **不能**作为 mobility 的 treatment。这一列必须用真 copy 重做。

### P1（加固）

| ID | 实验 | 回答什么 |
|---|---|---|
| P1-1 | eligibility funnel | 分母用全部到达请求，逐条统计 empty/idle、boundary、KV、snapshot、gain 的失败数。决定要不要做非空导入 |
| P1-2 | 闸门消融 | always-import / cost-only / capacity-only / both；不可行动作安全回退；报 decision regret |
| P1-3 | 受控拥塞 | 源引擎施加已知负载，测 prefill vs copy 交换比是否扩大。把一次意外观测升级为结论 |
| P1-4 | 生命周期 | 多轮 group reuse、端口、显存、源回收；失败/超时/取消。当前每次迁移泄漏一个 NCCL 组——必须作为 limitation 报告 |
| P1-5 | 源回收验证 | 所有权变更 ≠ KV 已释放；观测迁移后源侧实际回收 |

### P2（广度）

长度 × 占用扫描（控制绝对 free 或 free/demand 比值，**不要**固定占用比例，
否则长度效应与准入可行性混淆）、第二模型/拓扑、混合租户负载、p99 尾延迟
（需足够重复，3 样本不能报 p99）。

## 3. 已确立的数字（引用时必须带口径）

### 3.1 重算成本 R(n)（prefill 到首事件，已剥离 decode）

| n | R(n) s | s/token |
|---|---|---|
| 8,192 | 0.902 | 1.10e-4 |
| 16,384 | 1.795 | 1.10e-4 |
| 32,768 | 3.959 | 1.21e-4 |
| 65,536 | 10.205 | 1.56e-4 |
| 98,304 | 18.219 | 1.85e-4 |
| 130,048 | 28.236 | 2.17e-4 |

**形状**：近似线性、略超线性。**不要**声称"从 8K 到 130K 严格线性"——
长度涨 15.875 倍而时间涨约 31.3 倍。用实测插值或分段拟合。

校准细节：用过原点拟合会得 7.85e-5 s/token + 0.20s 固定项，低估短 prompt；
应取顶段边际斜率 8.78e-5。token 数必须取服务端 `usage.prompt_tokens`。

### 3.2 搬运成本 C(n)（transfer 相位，**不含 group init**）

| n | C(n) s | 线 | 带宽 GB/s |
|---|---|---|---|
| 4,096 | 0.472 | E | 0.29 |
| 20,480 | 0.473 | E | 0.96 |
| 65,536 | 0.550 | A | 2.22 |
| 98,304 | 0.678 | A | 3.06 |
| 130,048 | 0.992 | A | 2.80 |

**正确表述**：在已测范围内增长显著慢于重建，固定开销主导，**不是与长度无关**。
payload 涨 31.75 倍而时间涨约 2.1 倍。跨节点 130K 为 0.907s（快于同节点 A 的
0.992，慢于同节点 B 的 0.826）→ 只能说"跨节点不劣于同节点"，不能说"每格不输"。

⚠ 130K 拷贝时间在不同记录里是 0.732 / 0.826 / 0.907 / 0.992，是**不同配对**
（同节点 pair / 同节点 B / 跨节点 D / 同节点 A）。引用必须带是哪条线，
**不能平均，不能混用**。

### 3.3 容量核算（单引擎 max_total_tokens = 262,144）

驻留 32K 前缀数 0→6 时，空闲槽 262,144→65,536，每步精确减 32,768，无驱逐。
**"满载"的定义：7 个驻留前缀时剩 32,768，恰好还能容纳一个最大请求。**

**P0-1 配对 2×2 实测（2026-09-30，单引擎、引擎角色跨 rep 轮换、
两臂驻留前缀数相同、4 reps/格）：**

| cold，引擎空 | 3.008 | 3.006–5.590 | 229,376 | — |
| **hit，引擎空** | **0.623** | 0.618–0.624 | 229,376 | — |
| **hit，引擎满载** | **0.623** | 0.620–0.628 | 32,768 | **7/7** |

### 3.6 端到端：路由 vs 搬运（2026-10-01，本轮新增）

**这是全文最重要的一张表：同一个 router、同一批到达、同一批引擎、
同一份 trace，唯一差别是放置规则与 mobility 开关。**

设置：3 引擎同节点（`27:31781/31782/31791`，各 TP2）、6 stream / 54 请求、
`hot_frac=0.5`（最长的 3 条 stream 全部钉在引擎 0，制造负载重力）、
TTFT 到首 token（decode 已剥离）、SLO = TTFT ≤ 10s。
产物：`results/p03-e2e.json`、`experiments/fluidkv/p03_real_copy_e2e.py`。

| 臂 | p50 | p90 | p99 | SLO@10s | goodput (req/s) | wall |
|---|---|---|---|---|---|---|
| **sticky**（亲和） | **1.20s** | 3.62s | 11.60s | **98.1%** | **0.891** | 59.5s |
| **least_loaded**（均衡） | 5.03s | 15.80s | 27.46s | 68.5% | 0.280 | 132.3s |
| least_loaded+move | 7.00s | 18.01s | 88.16s | 70.4% | 0.075 | 509.6s |

**读数 1（承重，可进论文正文）：纯路由的两难被量化了。**

⚠ 所以 affinity **不是**一个可被忽视的基线：在这份负载上它是**最强**的。
论文不能写"我们的方法比路由好"，只能写"我们让均衡不必再付状态重建的代价"。

**读数 2（本轮负面，必须如实报告）：搬运臂 4 次尝试、0 次成功。**

p99 反而到 88.16s。**这不是机制失败**——机制在隔离环境下已跑通（读数 3）。

| `src_has_no_runnable_prefix` | 6 | 源端确实无可搬运前缀 |

### 3.7 隔离环境下的完整迁移链路（2026-10-01）

`/tmp/repro.py`，2 stream，逐步打印，同节点对 `27:31781 → 27:31782`：

### 3.8 根因：process group 泄漏（本轮最重要的系统发现）

`hygon_hybrid_control.py:31`：

```python
self.groups = {}          # 只增不减，从不 destroy，无上限
```

每次 `init_group` 都新建一个 NCCL process group 存进去（`:189`），
**永不销毁**。实测退化曲线（同节点对，反复 fresh init）：

| 状态 | init 实测 |
|---|---|
| 全新引擎 | 0.06 / 0.10 / 0.11 / 0.12 / 0.14 s |
| 反复 fresh init 后 | 5.7 → 20.8 → 26.1 → 31.2 → 32.2 s |
| 继续加压 | 92.3 → 163.3 → 186.9 s（超时）→ **引擎不可达** |

**⇒ 三层结论：**

1. **传输不是瓶颈，group 生命周期才是。** `per_transfer` 恒在 0.2–0.6s；
   劣化的永远是 init。已有工作（Preble / CacheRoute）从不搬运状态，
   所以**根本不涉及这个问题**——这是 mobility 独有的系统成本。
2. **成本模型须区分"复用"与"新建"。** 复用 group：`C ≈ 0.2–0.6s`（可接受）。
   每对新建：`C ≈ 20–190s` 且不可恢复。**协调器的 `_ensure_group` 短路
   因此不是优化，而是正确性前提。**
3. **失败不可重试，且会级联污染。** `TCPStore` 握手是非对称的
   （`:169`）：连不上的一端**永久阻塞**；而引擎的 hybrid 控制通道是
   **单队列**，于是这个阻塞会拖死该引擎的**所有后续请求**。
   实测：一次失败的 init 会让后续所有 init 立即失败、最终引擎不可达。

⚠ **这解释了我此前一整轮的反复挂死**，也解释了 storyline 旧版
16–31s 的来源：那些"裸建链"测量是在已降级引擎上做的。

## 4. 设计：三个组件

| 组件 | 名称 | 真正要回答的问题 | 状态 |
|---|---|---|---|
| 时机 | **Tool-Gap State Preparation** | 哪次工具调用值得提前准备？窗口不足/提前返回怎么办 | 提案 + 部分实现 |
| 位置 | **Load-and-State-Aware Placement** | 综合源端排队、目标负载、已有状态与准备成本选目的地 | 部分实现（`preparation_decisions.py` 已有 `max(ready,queue)+service`） |
| 落地 | **Budgeted Runnable-State Handoff** | 同时预留 KV + snapshot + 临时缓冲 + decode 预留；何时发布；失败如何回退 | 提案 + 空目标导入已验证 |

**第三项的实质（这才是贡献，而不是"容量闸门"）：**
现有工作里 Preble 已经把驱逐后的重算成本计入 load cost，CacheRoute 已有
warm-set admission 与等大小 slot 预算。所以"要看容量"**不是新的**。新的是：

1. 资源是**向量**：(KV token slots, snapshot slots, 临时 gather/scatter 字节,
   decode 增长预留) 必须同时满足；
2. 迁移期间**源 pin 与目标 reservation 同时驻留**，瞬时占用上升；
3. commit 后**源是否真的释放**必须有观测（所有权变更 ≠ KV 释放）。

## 5. 必须如实报告的负面结果

1. **【2026-10-01 新增，最重要】稳态下搬运几乎无法触发。**
   三臂端到端里搬运臂 4 次尝试、0 次成功：`dst_not_empty` 25 次、
   `src_has_no_runnable_prefix` 6 次。根因是引擎硬约束
   （`hygon_hybrid_control.py:221`：`destination cache must be empty`）。
   **稳态负载下每个引擎都有驻留前缀，所以"目标为空"几乎永假。**
   ⇒ 论文**不能**声称"常态负载均衡"。能证明的是
     **scale-out / 新 worker 预热 / 冷引擎接纳**——即负载重力留下空位的场景。
   这与 `eligibility-funnel` 的 5.6% 是同一个约束的两种量法。

2. **affinity 是最强基线，不是弱基线。** 端到端 sticky 的
   p50 1.20s / SLO 98.1% / goodput 0.891，全面优于 least_loaded
   （5.03s / 68.5% / 0.280）。**所以论点是"让均衡不必付状态重建代价"，
   不是"我们比路由快"。** 任何写着"路由方法不够好"的措辞都要删。

3. **process group 泄漏，且失败不可重试。** 每次新建 group 永不销毁
   （`self.groups` 只增不减）；`TCPStore` 握手非对称，失败端永久阻塞，
   而 hybrid 通道是单队列 → **一次失败 init 拖死整个引擎**。
   实测 4 次把引擎搞到不可达。这是当前实现的硬限制，必须进 limitations。

4. **请求变快、任务不变。** 71K 前缀迁移把该请求 TTFT 从 11.497s 压到 3.944s，
   但轮次完成时间 125.350s → 125.324s 几乎没动。关键路径在别处。

5. **mobility headroom 窄。** 记录的 59.81%/64.62% 来自
   `oracle/ceilings.py`，其中 B1 用全局已见 block 集合、不模拟迁移与容量约束。
   审计给出了一个反例：单引擎两个 stream 相同前缀时 B0=0、B1>0，而根本不存在
   跨引擎迁移。所以 4.8pp **不能**叫 mobility 上限。
   **P1-1 已用真判据重算（`results/eligibility-funnel.json`）：**
   1,152 条到达请求中只有 **65 条（5.6%）** 满足"远程可复用 ∧ 高于 L\* ∧
   容量可行 ∧ 净收益为正"。主损失是 `stays_on_home_engine`（734 条，63.7%）。
   ⇒ 这个 5.6% 取代 4.8pp 作为**可行动覆盖面**。

6. **跨节点配对的 init 不稳定。** 6 引擎跨 3 节点时，一次 init 失败即级联，
   全部臂无法完成。已收敛到同节点 3 引擎拿下主结果。
   跨节点 130K 传输本身已验证（1.19GB / 0.37s），但**多节点端到端尚未跑通**。

7. **场景受限。** 后端只支持向空引擎导入（要求 idle、目标无 children）。

8. **输出一致性。** batch 形状影响数值，逐 token 一致率需单独报告，
   长度正确 ≠ 语义等价。

## 6. 与现有工作的准确边界

| 工作 | 已核实的能力 | 我们不能再写什么 |
|---|---|---|
| Preble | 按复用 token 数调度，load cost 内含驱逐后重算 | 所有 router 都把命中当 boolean、都不看容量外部性 |
| CacheRoute | warm-set admission；**明确不 reserve/migrate KV**，承认异质前缀大小超出等 slot 模型 | admission 是我们首创；CacheRoute 完全没有容量预算 |
| DualMap | 自适应 hash-prefix、SLO-aware dispatch、hotspot rebalance | 静态超参无法响应偏斜；不区分前缀 |
| Llumnix | 迁移活动请求与内存状态 | state migration 是全新自由度 |
| Mooncake | KV-centric 调度、分离式缓存与传输 | 全领域只有 request routing |
| HYPIC | hybrid attention 的 recurrent-state reuse | 混合状态一致性问题从未被注意 |

**更窄而真实的切口：** 所选路由器的 action space 不包含我们实现的、经过正确性
验证的 hybrid runnable-bundle import；我们研究给这个 action 加上实际资源约束后，
何时值得使用。
