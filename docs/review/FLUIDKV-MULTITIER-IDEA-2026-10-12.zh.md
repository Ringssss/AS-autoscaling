# FluidKV 多级状态准备：idea 探究

> 历史/提案留档：以[技术总览](../FLUIDKV-TECHNICAL-ARCHIVE.zh.md)标明的证据状态和最新结论为准；未实施的方案不代表已有能力。

2026-10-12。依据 `/home/zhujianian/blog.md`、六实例结果、已有 Fluxon 定版源码审阅以及本次查阅的官方资料。本文是研究假设与设计草案；本轮未启动新 GPU 实验，也未实现多级数据面。

## 判断

值得探究。多级缓存使调度从“已有 HBM 状态在哪个 worker”扩展为“通过什么路径、何时、用多少资源使状态在目标上可执行”。但新增 HBM/DRAM/SSD 标签、全局目录和 min(加载,重算) 公式，本身不足以构成论文新颖性。

博客已经提出动态搬运积压与影子记账；应明确归因。我们的潜在推进点是：将共享的状态准备动作及其消费者依赖纳入同一个决策，联合选择恢复/重算、目标实例与请求接纳时刻。是否超出现有工作，需要进一步逐机制核对，当前不声明首创。

## 现有工作的边界

- [Mooncake FAST'25](https://www.usenix.org/conference/fast25/presentation/qin) 已研究 KV-centric 服务；其[架构文档](https://kvcache-ai.github.io/Mooncake/design/architecture.html)描述 DRAM/VRAM 间直接传输。不能以某个示例 proxy 的不足代表完整论文。
- [Dynamo 配置文档](https://docs.nvidia.com/dynamo/knowledge-base/modular-components/router/configuration-and-tuning)已有 host/disk 缓存权重与缓存/负载调优。因此“区分缓存层”已有直接先例，博客的版本限定也要保留。
- [Cake](https://arxiv.org/abs/2410.03065) 已提出并行且动态地计算与加载 KV，并适应其他请求和资源变化。简单二选一 cost model 不是空白。
- [ObjectCache](https://arxiv.org/abs/2605.22850)研究按层检索、跨请求传输/计算重叠和共享带宽下调度。不能将“考虑带宽争用”单独写成新贡献。

以上是问题边界核查，不是完成了全领域新颖性审查。

## 核心假设

HBM 之外的缓存命中保留了复用机会，同时引入恢复工作。多级存储缓解显存容量和固定 worker 亲和性，也可能让原先分散的 GPU 请求集中竞争 SSD、源端 DRAM、NIC 或 H2D。

候选创新假设：**在共享恢复资源和多消费者条件下，逐请求独立选择“当前看起来最快的路径”会形成额外积压和重复工作；联合调度共享准备动作与消费者接纳，可以改善全流量 SLO goodput。**

“一次命中并不等于立即可执行”具有两层含义：数据可能尚未进入目标 HBM；对 hybrid 模型，所需 recurrent 状态与执行边界也必须匹配。目录中的存在、在途承诺和已确认可用必须分开。

六实例实验给出了相关但有限的证据：96 并发时，异步重算约71秒；等待准备完成再路由约50秒；复制约45秒。等待不后移请求到达时间，全部计入延迟。实验中异步重算仍出现5个冷前台请求，表明只登记准备负载不足以防止重复工作。这还不是多级缓存收益的证明。

## 三组件

| 组件 | 负责的决策输入/输出 | 具体新增问题 |
|---|---|---|
| 全局状态与资源视图 | prefix/状态版本、真实驻留层、兼容执行边界；资源容量、积压、在途动作及订阅者 | 缓存存在、数据可读与目标可续算不是同一状态；多个目标可能共享同一源或链路 |
| 恢复计划与代价评估器 | 为候选 worker 生成本地复用、远端加载、GPU复制、重算、加入在途准备等可行计划，返回就绪时间与资源占用 | 代价随其他承诺变化；内存可用、执行队列与数据就绪要一起估计 |
| 准备—路由—接纳协调器 | 合并重复准备、选择目标和副本数、提交动作、登记依赖、确认就绪后放行、终态回滚 | 独立决策会重复计费/重复加载；过早放行会重复 prefill；过晚会浪费重叠机会 |

现有 GPU-direct runtime 和可复用的 Fluxon 数据面作为执行后端。不要把 cost model 拆出来只为凑贡献；它必须显著减少错误决策，才能成为独立贡献。

快路径比较少量候选并加入已有准备；慢路径根据需求和资源压力调整准备队列、副本及热状态驻留。两者共用同一套承诺和终态，不维护互相矛盾的资源账。第一版限制只读候选数量，避免重新引入上一轮的元数据查询瓶颈。

## cost model 的最低要求

计划是 `(目标worker, 状态来源, 准备方式, 合法复用边界, 依赖动作)`，不能只返回“迁移/重算”一个 bit。

第一版针对必须先完成准备才能续算的实现，用下面的依赖结构估算：

`预计首token时刻 ≈ max(状态就绪时刻, GPU可接纳时刻, 目标HBM容量就绪时刻) + 剩余prefill耗时`

这些时刻必须在提交该候选计划后的资源承诺下估算。重算本身消耗 GPU；加载后的 HBM 占用可能触发其他状态驱逐；目标 decode 干扰也必须进入计划比较。

对单个串行、FIFO 资源，可以从 `(排在前面的剩余字节 + 本动作字节)/有效服务速率` 开始校准。它不是任意共享链路的精确模型。SSD→DRAM→网络→HBM 可能分块流水，应以实际依赖图的关键路径估计，避免把所有阶段的完整时长相加或一律取最大值。

比较方案至少包括：继续在温热源端排队；从可用层恢复；直接重算；等待或加入已在途准备。待运行时支持合法分段时，再比较部分加载/部分重算；hybrid 状态不能假设任意 token/layer 边界都可独立拼接。

同一目标、同一状态的一次准备可以服务多个消费者，准备资源只记一次，每个消费者的后续 GPU 工作分别记。复制到不同 worker 仍有各自的目标内存和末段传输成本。不能简单将总字节数除以消费者数就宣称搬运免费。

## 借用 Fluxon 的方式

沿用已有审阅的固定 commit：`cc800babb844092362d10369eacb6aa0685f1fde`。该版本已有 GetStart/GetDone/GetRevoke、真实容量 reservation 和在途终态管理；不能把这些借来的能力算成我们的原创。

控制器需要无副作用的候选 Probe；最终选定计划才调用创建真实承诺的接口。影子资源账用于预测，数据面 reservation 用于实际所有权，以动作 ID 对齐，避免双重扣账。GPU 可续算边界、消费者依赖和 GPU 接纳仍由 FluidKV 接通。

DRAM 路径应成为正常候选。CPU 负责调度不能推出 CPU 内存不可用于 KV；GPU-direct 的价值需要实测比较。

## 首轮探究：限定三个问题

1. **选择是否随争用反转？** 固定模型、上下文和缓存分布，逐渐增加一条真实共享 NIC/H2D 路径上的背景流量，比较等待 HBM owner、恢复、重算的完整延迟。检查最佳静态权重能否覆盖变化，而不只画裸带宽曲线。
2. **逐请求判断是否输给共享准备？** 同一份状态的多个消费者与不同状态消费者分别测试；比较重复请求、已有 single-flight 合并、动态代价、动态代价加依赖接纳。合并传输本身是常见机制，必须对照具备它的基线。
3. **独立阶段优化是否留下可消除的损失？** 同样的数据面、候选动作和观测下，对比“先选worker再恢复”与联合选择worker/来源/准备/接纳。覆盖持续流量与自然驱逐，报告前台及被干扰后台请求的整体 SLO goodput。

先接 HBM、本地DRAM、远端DRAM；只有实测显示 SSD 改变瓶颈或计划选择时再接 SSD。多层场景里仍保留 Blitz/DualMap 作为参照，同时加入真正具有分层缓存能力的路由/恢复基线，以及准确代价下逐请求贪心的强控制。

继续标准：联合决策相对这些强控制在动态资源条件下仍有可重复收益，且元数据/调度开销不吞掉收益。若调好分层权重或补上普通 single-flight 后差距消失，就止于工程集成；不要继续靠增加层数包装论文。

## 工作版 storyline

长生命周期推理不断产生可复用状态，HBM 容量限制使状态跨层保存。多级存储保留了历史计算，却使复用依赖一条共享且拥塞程度变化的恢复路径。请求选择执行位置时，也在承诺存储、网络、内存及 GPU 工作；一份准备又可能服务多个请求。因此，系统需要联合安排状态准备与消费者执行，依据目标可续算时间选择加载、重算或等待，并在真实就绪后接纳请求。

FluidKV 的研究目标是把这种依赖纳入统一调度。已有 HBM 复制是其中一条执行路径；多级缓存支持、共享资源代价模型与联合调度收益尚待实现和验证。
