## 1. 现象：KV-cache gravity

LLM 请求能够复用 system prompt、会话历史与 Agent 公共前缀留下的 KV。缓存亲和路由减少重算，也让后续计算集中到已有状态的 worker。共享前缀的并发需求或不同会话的负载变化，使状态位置与空闲计算容量发生失配。

缓存亲和性有真实价值；负载均衡需要支付改变执行位置的准备成本。长上下文和冷热不均分别只能说明潜在条件，二者同时发生且落在完成时间关键路径上才构成收益机会。

## 2. 现有方法怎样处理

按观察状态、选择当前落点、调整未来状态三个维度组织相关工作。Preble、DualMap 和 Blitz/LMetric 分别用不同的候选集合、命中与负载估计处理当前请求；路由到冷节点后，重算自然留下副本。Mooncake 等系统提供远端状态复用和数据搬运能力。Llumnix 研究运行中重调度与状态迁移。KVFlow、SAGA 已考虑工作流结构和未来状态使用，proactive 本身不能成为区别。

博客对特定代码版本的功能缺口可作为复核线索；公共示例 proxy 不代表论文完整能力，功能排名不代表性能排名。相关工作不得写成“现有系统完全不考虑状态、未来或搬运成本”。

## 3. 需要解决的问题

一次准备的价值取决于在目标状态就绪后，有多少后续计算能够利用该目标的剩余容量。准备会占用网络、显存和计算资源，改变原先使目标有吸引力的负载条件。多个请求还可能共享同一份准备。

研究问题：有限资源下，为哪些未来消费者、在哪些 worker、何时准备哪些共享的可续算状态，才能相对于最好的不准备执行方案缩短完成时间？

最好的替代方案包括留在已有温热位置、路由后重算、提前重算及已有可用远端副本。不能把所有迁移一律与冷重算相比。

## 4. 新挑战与三个组件

| 挑战 | 组件 | 具体责任 | 当前状态 |
|---|---|---|---|
| KV 重叠、正在准备和真正可续算具有不同语义；hybrid 状态需要一致执行边界 | Executable State Directory | 标识共享前缀、续算边界、KV/recurrent 状态与已确认/在途位置 | SnapshotDirectory 和状态描述已有基础；跨全部数据面的一致观测仍需实现 |
| 准备收益由多个消费者共享，准备成本又竞争相同资源 | Preparation Scheduler | 快路径路由与接纳；慢路径按最佳替代方案计算边际收益，合并共享准备，维护资源承诺，支持不准备/复制/重算 | 本轮统一后端与原版策略对照已接线；共享准备优化和持久资源账本属于待实现设计 |
| 搬运完成未必意味着可安全执行；失败不能留假副本和永久占用 | Relocation Runtime | 容量准备、传输、执行边界验证、发布、失败回滚 | 协调器已有 prepare/copy/commit 基础；实测 DCU 路径仍要求 idle 与空目标 |

三者通过同一动作 ID 连接：目录说明需要什么，调度器决定是否值得准备，runtime 提交真实结果。影子负载是控制器估计，数据面持有实际资源；两者以事件核对，避免双重预留。使用预估完成时间时不声称硬 SLO 保证。

## 5. 核心 insight

KV 副本的价值，是它在需求窗口内新增了多少可实际使用的计算容量。状态准备把历史执行形成的局部性变成可调整的调度条件，同时也消耗资源。需要联合考虑消费者、状态共享、目标容量和准备时间。

这是一项待验证研究假设，必须对照 KVFlow/SAGA 等完整方法细化新颖性。快慢路径、GPU-direct、回滚和“state first class”各自都不足以单独构成新贡献。

## 6. 可用于 Introduction 的工作段落

Agent 工作流在多轮执行和分支之间复用计算状态。缓存亲和路由能够利用已有状态，但需求变化时，可复用状态的位置可能与可用计算容量分离。复制或重建状态能够扩大执行选择，同时占用带宽、显存和计算资源；多个消费者还可能共享同一次准备。因此，系统需要联合调度状态准备与后续执行。FluidKV 以共享的可续算状态为准备单位，结合消费者需求、执行边界和实时资源承诺，选择准备的位置与时机，并将完成后的状态交给在线路由使用。

最后一句描述目标设计。只有组件实现和实验完成后，才能改成已完成贡献。
