## 2. 阻断论文论证的问题（按严重性排列）

### P0-1：所谓“miss 让 7/7 邻居消失”来自 missing-value 绘图错误

直接证据：

- `experiments/fluidkv/capacity_vs_hit.py:133` 之后只在 `hit_tight` 下检查存活；miss 的 `surv` 始终为 `None`。
- `results/capacity-vs-hit.json` 三个 miss 的 `survivors` 全为 `null`。
- 修正前 `plot_capacity_vs_hit.py:80` 附近使用 `if surv else "0/7 alive"`，把缺失值变成零。
- hit 的七个被检查对象包含 target 本身，因此不是“七个邻居”；另外的邻居只有六个。

**撤回：**“0/7 alive”“摧毁整个工作集”“保护七次邻居重算”。它们不是弱证据推断，而是记录根本没有提供该观测。本次已修正绘图脚本，unknown 明示为 unmeasured，原始 JSON 不改。

### P0-2：free slots 减少不是 eviction 数量

miss 从 32,768 free 变为 4,096 free，差值 28,672 是**净分配占用增长**。基本会计关系为：

`F_after = F_before - allocations + frees`。

eviction 释放槽位，方向是增加 free；只知道 free 减少，无法反求 eviction。目标请求开始前有 32,768 free，旧叙述却拿请求结束后的 4,096 当成到达前可用容量，颠倒了时间顺序。hit 前后 free 相同，也不能写“本次 hit 又消耗 32K”。

即使以后观察到完整命中消失，也要区分 KV eviction、snapshot eviction、最长完整边界回退和 inspect 可见性；“不再 full”不等于全部 KV 字节被驱逐。

**可写：**miss 条件请求结束后 free 槽位净减少 28,672；eviction 及邻居损失尚未测量。当前占用是 token 池的 87.5%，不能写成整张卡 VRAM 已满，更没有证明 snapshot 池同时饱和。

### P0-3：capacity pilot 不是“唯一变量为 residency”的配对实验

`capacity_vs_hit.py:29` 将 cold/hit/miss 固定到三个不同引擎；`:149-153` 用不同 base 的 token 区域；`:127` hit 用 slot 0、miss 用 slot 20。相同的是名义长度和两个 occupied 条件的初始 free 数，不是完全相同的请求。MoE 输入内容、引擎差异、运行顺序都没有交叉抵消。

`ttft()` 在第一条非空 `data:` 就停表，没有确认包含输出 token；读取完整响应后才 inspect，因此 free-after 是**生成完成后**，不是 TTFT 时刻的容量。`install()` 把生成参数放在 `sampling_params`，`ttft()` 却放顶层；需核实服务端到底接受了什么。不能先认定是引擎“忽略短生成”，再由此推导缓存规律。

观察中位数：cold 3.960650s、hit 1.667515s、miss 9.542520s；miss/hit=5.722599，差 7.875005s。这些数可以保留为 pilot。`9.54-3.96` 不是已识别的纯 memory-pressure penalty，更不能说“尚未计入 eviction”：客户端延迟已经包含其区间内发生的操作。

“hit 比 cold 快”是缓存预期行为；`3.96-1.67=2.29s` 也不能推出“驻留价值大于 cold R(n)”。原文比较的是不同基准下的差值。

### P0-4：0.45s 的固定开销解释与计时边界冲突

`mobility_sweep.py:migrate()` 先完成 `direct_group/init`，然后调用 `direct_transfer`，最后取 destination 返回的 `transfer_seconds`。

`hygon_runtime/hybrid_control.py:147-218` 显示：容量分配和 prepare metadata 握手发生在 `started = time.perf_counter()` **之前**；`init_group()` 更是另一 API。计入的是 gather/pack、broadcast、scatter、同步、插入和 ready 等阶段，不能说这个测量从 group initialization 开始。首次 broadcast 仍可能有惰性初始化，但没有分项计时就不能归因为 communicator 创建。

三个不同量必须分名：

1. `C_engine`：当前 transfer_seconds；
2. `C_ready_wall`：选择动作到目标 ready，包括初始化、预留、RPC、验证；
3. `T_first_token_move`：上述路径加等待/剩余 prefill/首 token。

当前用 client cold TTFT 除以 `C_engine` 是**不同终点的机制成本比**。28.7× 不能叫迁移后的 TTFT 加速，也不能直接用来决定服务侧盈亏。完整 prefix 可运行仍不意味着“无任何前向计算即可发首 token”。

### P0-5：4.8pp 不是 mobility headroom；0% 不是跨流共享上限

真正来源是 `oracle/ceilings.py`，不是 FINDINGS 指向的 `frontier.py`：

- B0 只在同 key 的历史请求中寻找最长前缀；计算了 home 但没有拿它统计同引擎其他 stream 的复用。
- B1 使用全局已见 block 集合；不模拟迁移、不约束容量、不加入队列、快照边界、传输或回收。
- B2 统计任意位置重复 block。B2-B1 是这个 workload 上“任意重复”与“前缀可复用”的差，而不是跨流共享收益。

**可运行反例：一个引擎，两个不同 stream，完全相同前缀。** B0=0、B1>0，但一个引擎根本没有跨引擎迁移。审计脚本直接提取当前三个函数执行该反例，输出 B0=0、B1=32 tokens。这已经足以否定该差值的 mobility 解释。

记录的 59.81% 和 64.62% 可暂作两种复用统计，不能叫 perfect-placement 上界。`decompose.py` 的 own 又只看紧前一请求，和 B0 的所有历史最大值不同。另有 `simulate.py` 的 BLOCK=16 与 `frontier.py` 的 NATIVE_BLOCK=64，需追溯 materialization，不能在稿件笼统宣称所有输入均为 native 64-token。

“120/384 完全冷，26.8% input tokens”只适用于该采样/截断及历史范围；LCP 与一个前驱为零并不等于全局不可复用。即使确实无可复用前缀，冷请求仍可能因其他请求少重算而少排队，所以不能宣称 mobility 对它们的 latency 毫无影响。

### P0-6：现有工作的描述不成立

本次核对一手论文（访问日期 2026-09-30）：

| 工作 | 核实的能力 | 我们不能再写什么 |
|---|---|---|
| [Preble §4.2 / Algorithm 2](https://arxiv.org/html/2407.00023v1) | 依复用 token 数调度，并在 load cost 中加入缓存驱逐后的重算成本 | 所有 router 都将命中视为 boolean、都不看容量外部性 |
| [CacheRoute §3.1–3.2](https://arxiv.org/html/2608.19677v1) | warm-set admission、等大小 prefix-slot 预算；明确不 reserve/migrate KV，且承认异质 prefix 大小超出 equal-slot 模型 | admission 是我们首次提出；CacheRoute 完全没有容量预算 |
| [DualMap §3](https://arxiv.org/html/2602.06502v1) | 自适应 hash-prefix、SLO-aware 动态 dispatch、hotspot rebalancing | 静态超参意味着不能对偏斜做动态响应；完全不区分前缀 |
| [Llumnix](https://www.usenix.org/system/files/osdi24-sun-biao.pdf) | 迁移活动请求和内存状态 | state migration 是现有系统没有的新自由度 |
| [Mooncake](https://arxiv.org/abs/2407.00079) | KV-centric 调度、分离式缓存和传输基础设施 | 全领域只有 request routing，无跨实例状态搬运 |
| [HYPIC](https://arxiv.org/abs/2607.01299) | 专门讨论 hybrid attention 的 recurrent-state reuse 与 position-independent caching | 混合状态一致性问题从未被已有工作注意到 |

这里不声称这些系统已经实现了与 FluidKV 相同的 completed-boundary 迁移协议；恰恰要沿这个具体差异继续比较。HYPIC 应进一步阅读全文与 artifact，摘要足以确定必须相关，但不足以裁定其迁移能力。

更窄而真实的切口：**所选路由器的 action space 不包含我们实现的、经过正确性验证的 hybrid runnable-bundle import；我们研究给这一 action 加上实际资源约束后，何时值得使用。** 是否有新意仍需机制与直接相关系统的能力对照，不能仅以换模型名称建立 novelty。

### P0-7：最新端到端表的“DualMap”需要降名，且没有 FluidKV treatment

与 `REAL_FINDINGS.md` 对应的 `real_compare.py:104-108` 中，名为 dualmap 的策略是两个 key 哈希候选中选累计 busy 小者，不是 `DualMapAdapter`：没有论文级 prefix-hotness/SLO routing 路径。`:126` 的 busy 在请求完成后累加，未在派发时记入在途工作。因此它不是实时 queue estimator。

应标注为 **two-choice hash heuristic** 并保留报告；不能当作 DualMap 原版实验。仓库另有接 upstream 的 adapter 和 one_hour 路径，不能因同名就混用。balanced 在这里也不是论文 setup 声称的 round-robin。

balanced 216 请求与 hotspot 405 请求采用了 closed-loop 并发/顺序约束，不能默认同一外生 arrival trace，也不能把达标比例 % 命名为 goodput（后者应以达标成功请求/s 报告）。原始表含失败，论文表删掉了 err 列；`real_compare.py:209-211` 还先剔除非有限TTFT，再计算达标比例，因此失败请求未进该分母。1pp 的次序翻转没有重复区间，不是“静态路由必然失效”的证明。

当前端到端表没有实际执行 copy 的 FluidKV 一列。`sticky+move` 是 reroute。已有其他真实迁移 pilot 可作为机制案例，但不能补成该表的 treatment。

### P0-8：capacity 动机与机制可行域错位

Hygon `validate_runtime()` 要求 idle，`transfer()` 要求 destination 无 children。该路径能证明的是**向空引擎导入状态**；不支持把可运行状态装进有其他租户的非空缓存。

如果为了迁移先 flush 目标，实际损失可能远超保住的状态。这必须计入政策成本，而非实验预处理隐藏掉。capacity admission 还应同时考虑 KV slots、recurrent snapshot slots、临时 gather/scatter buffer、decode 增长和预留中的状态。

最务实的两个选择：

- 保留当前机制，收窄为 scale-out / fresh-worker warm start，用公平 GPU-seconds 成本衡量空目标资源；
- 主张常态集群 load balancing，则实现并验证非空目标 import、并发 reservation 和失败 rollback。

这两个方向不能只靠文字折中。目前推荐围绕“runnable-state mobility 的可行域”写机制章节，同时以第一个场景形成最短实机闭环；第二个作为明确的系统扩展，不提前宣称已具备。

## 4. 真正值得深化的 insight

### 4.1 缓存命中应以可执行状态为单位

原始 LCP、可复用 attention KV、存在 recurrent snapshot、可迁移边界、能在目标继续执行，是不同谓词。值得研究的是这几者不一致时，传统 token-based 估值会做错多少次决定。

用 n_raw 表示 token LCP，b 表示已存在完整状态的边界；一般 `b <= n_raw`。必要条件不仅是 tokens 相同，还包括状态对应同一位置/分支、KV与snapshot同时可见、布局兼容。**“position-aware”若保留，必须精确定义成这个位置边界，不要与 position-independent caching 混淆。** 若设计没有比 boundary check 更多内容，名字用 runnable-prefix 更准确。

### 4.2 迁移资格可能比带宽更限制收益

有效覆盖率是若干事件的交集：有可复用远程状态 ∩ 有完整边界 ∩ 目标容量可预留 ∩ 源可访问 ∩ 满足运行时限制 ∩ 净收益为正。

当前 idle+empty 约束可能把覆盖率削到很低。优先画 eligibility funnel，计数分母用所有到达请求，并另报 token/估计节省时间权重。这比继续让已可迁移对象快几十毫秒，更能解释为何微基准优势没转成系统收益。

### 4.3 迁移阈值是“状态与负载条件的边界”，不是一个通用长度

每次请求比较三种行动：原地 warm serve、目标 cold serve、目标 import 后 serve。必须把 source wait、destination wait、完整状态准备、残余 prefill、首token和干扰放到相同终点。

长前缀也可能不该迁移：源无队列、目标更忙、目标要驱逐高复用对象或 snapshot 不足。短前缀也可能值得转移：源即将退役、目标已预留且准备可隐藏、原地等待很长。`n>L*` 最多是固定测试条件下的投影。

对于已经到达且已知前缀的请求，估计一次copy-vs-recompute可不预测未来。对于**等待未来重用的缓存保留/admission**，必须考虑 reuse probability/expected count、驻留时长和机会成本。稿件把这两类问题混在一起了。

### 4.4 容量是资源向量，并有迁移期间的双份驻留

`(KV token slots, snapshot slots, temporary device bytes, transfer reservations)` 应一起满足预算。迁移期间源pin和目标reservation通常并存，瞬时占用上升；commit 后是否真的释放源缓存必须有观测。

ownership 变更不等于 KV 已释放；source unpin 也不等于释放缓存。当前直接拷贝属于 replication primitive，配上源回收/所有权切换才构成相应意义的 relocation。内存总量极紧时，迁移甚至可能比重算更难被准入。

### 4.5 等长替换不自动“净负收益”

两个同样32K的前缀，重用概率、下一次到达、SLO slack、原地排队都可能不同。驱逐一个低价值条目换入已知要用的状态可能有利。保守的“不驱逐”gate是可实现的baseline，不能伪装成最优性结论。

可先定义总增益为：目标请求收益 + 其他请求排队改善 − 迁移干扰 − 被替代状态未来损失。这是设计模型，不是本轮已测结果。用seconds或显式utility统一量纲。

### 4.6 “请求变快、任务不变”应保留为关键反例

71K例子的请求TTFT降低，但round makespan几乎不动，是可靠的设计提醒。`BOTTLENECK.zh.md` 还指出116K关键请求首token后约97.36s，占其完成时间77.7%；因此当前稿件“profile证明瓶颈在prefill”的说法与引用记录相反。

这不是说prefill优化没用，而是主目标要选对：交互首token/SLO适合研究复用；若承诺agent任务完成时间，则必须分析依赖关键路径和decode。还要区分目标请求收益与对冷请求的队列外部性。

### 4.7 工具等待可隐藏迁移，但时间加权98%不足以预测覆盖率

16类工具每类一次/若干次微基准并非生产调用分布。“多数等待时间在重尾”不能推出“多数迁移都有足够窗口”。需要在真正eligible的迁移事件上计算 `P(window >= C_ready)`，并测工具提前返回和与传输竞争CPU/NIC/GPU的情况。

可以把proactive window作为可选优化；论文基本价值应在on-demand完整成本下先成立，否则研究范围必须明确限定有窗口的工作负载。

## 5. 推荐论文主张与组织

推荐工作标题：**FluidKV: Resource-Aware Runnable-Prefix Mobility for Hybrid LLM Serving**。这是待验证研究方向，不声称完整在线资源策略已经实现。

主张草案：混合模型跨引擎复用需要成套、位置一致的可执行状态；这种状态值得迁移与否，取决于目标容量和相对服务完成成本。FluidKV通过完整边界发现、成套状态安装和资源可行性判断，在定义清楚的迁移场景中保留复用并改变执行位置。

三个贡献位：

1. **可执行状态抽象与正确性协议**：哪些状态、哪个边界、何时发布、失败如何收回，以及为何KV-only不够。
2. **受资源约束的动作选择**：在同一服务终点比较stay/cold/import；只主张实际实现的gate，不将拟议策略写成已交付。
3. **运行区间的实机证据**：收益、无收益和损失都展示；报告全流量指标、eligible覆盖率和资源成本。

建议结构：Introduction；Background and Three Questions；Design；Implementation；Evaluation；Related Work；Limitations/Conclusion。当前 Background 是§2、Motivation实际§3；不要继续沿用会话里的“§2”导致错改。

动机只留三个问题：什么状态能复用？复制与重算在相同终点下谁更便宜？便宜的动作何时能改善系统？O1–O4合并为一张成本曲线；O5降成待配对验证的pilot；删除流水账式校准事故，把仪器细节放方法/附录。

论文初稿可以现在写：抽象、模型约束、协议、已确认的成本数据和negative case都有材料。摘要的系统收益句、全量evaluation结论与“first”声明留待证据闭环后写，不用精巧措辞填空。

## 7. 实现与写作的一致性检查

- `HybridMigrationCoordinator._ensure_group` 已按pair缓存组，不是所有路径每次迁移都新建组。Hygon sweep每cell新组且engine无teardown的结论应限定到该路径。
- pair端口基址按+1分配，而Hygon TP每rank有独立store/communicator，需按实际端口集合检查冲突。当前代码store为 `p + tp_rank + tp_size`，TP2涉及p..p+3，不是文稿的“一律三个端口”。运行镜像是否同版本仍需manifest确认。
- cached group绑定初始化rank角色，反向迁移同pair的role协商需要专门验证，不能仅因group可复用就称双向可用。
- 同步coordinator查success、token数和byte数后commit，不等于重新验证output/state digest；equal byte count不是equal contents。历史正确性smoke提供了更强的局部证据，应单列。
- model config/index hash不是完整weight-content hash，同名分片内容变化未必被捕获。若声称checkpoint identity，固定weights revision/content digest。
- `buffers()` 返回的 `(buffer,0)` 与 `(buffer,1)` 是索引维度axis，不是TP rank。稿件“20 buffers在rank0、2在rank1”误读了代码；各TP rank执行自己的buffer传输，需分别报告局部layout与聚合字节。
- raw sweep记录有source timing而未保留source bytes，不能由现有JSON独立复核每cell“两边byte-identical”。引擎协议的metadata一致性是另一层证据，不要混说。
- `flush_and_confirm_empty` 仅用一段probe无匹配推断空树，逻辑上不足；transfer端空树检查可拒绝，但不能替代benchmark前置验证。
- `observe_prefix` 返回完整snapshot边界，不是完整raw KV LCP；论文必须按API实际语义解释matched_tokens。
- “unmodified SGLang”错误：有自定义端点、scheduler dispatch和overlay。可写“不修改模型数学计算/不引入新模型kernel”，并提供patch版本。
- `\Lstar` 宏自带`$`却又在display math里使用，可能产生数学模式错误；检查不能只数美元符号。`sec:obs`引用无对应label；正文无正式bibliography/cite体系；大量figph只是占位，并未包含新PDF。
- “hit ratio和latency严格同序”与同页hotspot表相矛盾；“most requests share almost no prefix”与31.2%为冷也不是同一命题。
- 删除诸如“未来想写的论文”“Pattern 2 blueprint”“alternatives rejected”写作脚手架；短contribution应陈述事实，limitations解释适用域。
