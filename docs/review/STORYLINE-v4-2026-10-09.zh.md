# FluidKV / AgentShift：状态准备与执行的联合调度

> 历史/提案留档：以[技术总览](../FLUIDKV-TECHNICAL-ARCHIVE.zh.md)标明的证据状态和最新结论为准；未实施的方案不代表已有能力。

日期：2026-10-09。本文确定研究主线和验证问题；已有数据的范围见证据表。

## 1. 固定的主线

长生命周期 Agent 在推理与工具执行之间反复切换。模型计算暂时停止时，已有计算状态仍然占据内存；下一次计算的最佳执行位置会随负载、容量和 worker 集合改变。状态位置与算力供给未必同步变化。

因此，系统需要联合安排 **状态准备和后续执行**：决定保留原地、目标重算或迁移复用，在下一次计算需要状态之前进行准备，并在准备未完成时依据依赖逐步推进目标计算。

核心研究问题：

> 在有限内存和共享传输资源下，如何安排 Agent 状态的准备与接管，使已有计算成果及时服务于下一阶段的执行，并降低多轮任务关键路径上的等待？

建议英文定位：

> StateShift: Coordinating State Preparation and Execution for Agentic LLM Serving

Elastic relocation 是系统能力。只有在真实扩缩容、worker 退出或成员变化场景完成验证后，才把 elasticity 放进主要贡献和标题。

## 2. 更深的 insight

**状态的位置、可执行性、可用时间和所有权是不同的系统事实。**

- 字节复制到目标，未必已经形成引擎能够复用的前缀。10 月的 hybrid 修复需要重建快照链，只有最终快照与 KV 并不足以让消费者复用。
- 状态部分到达时，某些层的下一轮计算可以开始，而共享缓存发布和对外所有权提交仍可等待完整准备。
- 目标当前空闲，未必在状态准备完成时仍是更好的执行位置。
- 源端所有权转移，未必释放物理显存；共享前缀与缓存策略会继续决定驻留。

调度问题因而是：**下一次计算在何时、何处，能够使用哪些已有计算成果。**

路由是在当前条件下选择目标；状态准备可以改变未来目标的执行条件。它的收益依赖准备及时性、后续复用、目标负载及干扰，不能用复制带宽或迁移次数单独判断。

工具间隙提供提前准备时间，但并不等于引擎空闲，也不意味着传输没有资源成本。其他会话仍在服务，预留和复制会占用两端内存、网络与 HBM 带宽。

## 3. Introduction 的因果链

1. Agent 的计算状态跨请求存活，保留状态可避免重复计算。
2. 算力需求与负载随执行阶段变化，最适合下一轮的 worker 可能不是历史状态所在位置。
3. 缓存感知路由能选择已有副本或目标重算；迁移能复用已有成果，但准备成本和资源占用会限制这种选择。
4. Agent 生命周期提供提前准备机会，准备时长与工具返回时间却都不确定。
5. 下一轮计算按层消费状态，完整搬运并不总是开始计算的必要前提；正确的消费依赖必须满足。
6. 本文联合调度状态准备和执行，以有限预算控制暴露在任务关键路径上的准备时间与对其他任务的干扰。

英文核心段落：

> Agentic LLM workloads retain inference state across alternating compute and tool phases. As cluster load and available capacity change, the worker best suited for the next turn may differ from the worker holding its reusable state. We study how to coordinate state preparation with future execution under finite memory and shared transfer resources. Our design prepares state during execution gaps and advances destination computation as its dependencies become ready, with an explicit ownership commit before results become externally visible.

## 4. 一个统一的决策问题

动作至少包括原地复用、目标重算、完整迁移和渐进目标端执行。已有远端副本或共享缓存取回也是有效基线。

以工具返回为时间原点，一个粗略的完整准备模型为：

\[
\widehat T_{finish}(a,j)=\max(\widehat R_{a,j},\widehat Q_j)+\widehat C_{a,j}.
\]

这里 R 是动作 a 在目标 j 上的剩余状态准备时间；Q 是目标可提供所需服务的等待时间；C 是该动作下剩余计算时间。只有准备和等待确实能重叠时，才能取 max；资源竞争须反映在估计中。调度还要计入对其他任务的影响和容量可行性。

渐进路径不能机械套这个整体模型。在单串行计算阶段的理想化模型中，第 l 组的执行结束时间是：

\[
F_l=\max(F_{l-1},A_l)+C_l,
\]

其中 A_l 是这一组精确依赖状态的到达时间，C_l 是计算时间；F_0 包含工具输出就绪和目标调度。真实引擎还包含 TP 同步、通信与计算干扰、batching 以及公开提交。这个模型说明传输顺序应由消费依赖驱动，并提供可测量的机会边界。

## 5. 三个组件各解决一个环节

| 组件 | 决策或协议 | 验证问题 |
|---|---|---|
| 状态准备与目标选择 | 联合比较原地、重算、取回和迁移；估计复用边界、队列和完成时间 | 相比强路由基线，是否选择了更好的执行路径？ |
| 有预算的准备调度 | 准备时机、目标 KV / recurrent 预留、源 pin、网络优先级与失败取消 | 提前准备是否值得，是否挤压其他任务？ |
| 按依赖执行与接管 | 内部就绪事件、渐进目标计算、TP 一致就绪、所有权与输出提交 | 迁移未完成时能否缩短等待，同时保证正确性？ |

预测下一轮返回时间应使用可获得的在线信息，并报告误差。工具提前返回、晚返回或下一轮取消都是决策输入。比较无预测、保守准备与预测准备，避免把未来已知的回放当成线上预测。

## 6. 状态抽象与 hybrid 证据

Inference state 限定为继续模型执行所需的可复用运行时状态，包括 KV、recurrent / Mamba 快照以及执行边界元数据；不把工具进程、外部副作用、长期知识库都纳入本系统。

KV 的稳定前缀与 recurrent 状态的版本语义不同。迁移固定一个明确边界，目标消费同一进度对应的完整依赖。不同层可以不同时间就绪；对外接管仍有明确提交点。

第一版评估使用相同模型、兼容精度和 TP 布局。已有 hybrid 实现是实际模型的证据，不能用 toy buffer 替代正确性验证；也不能据此声称所有 hybrid 模型都已支持。渐进 Transformer 路径和同步 hybrid 路径是两个实现分支，通用协议需要逐项闭合。

## 8. 现有实验必须修正的口径

- p03/p04 的 busy 是累计完成请求耗时，没有记录在途工作；首批并发可能扎堆到同一个目标。
- p04b/p04c 从清空状态开始，只往 cold 集合生成，没有初始化 hot 端热点状态。
- TTFT 从 serve 内开始，遗漏 router wait、inspect、迁移；报告端到端时必须从完整请求到达开始。
- p03/p04 输出固定为 16 tokens，未按 AgentX 原始工具间隔回放；它们是选定前缀结构的受控回放。
- NaN 请求在部分 SLO 汇总中被排除；失败必须计入总请求分母。
- `realized_saving_s` 是 token 数乘固定 prefill 系数减复制时间的估计，不能称为实测净收益。
- 稳态迁移能力不能建立在 `evictable_token_slots == 0` 的“空树”猜测上，也不能把 inspect 失败作为目标为空。

## 9. 与已有工作的关系

“状态是一等公民”“主动预取”“边生成边复制”“按 deadline 传输”是动机或已有技术基础，单独使用不足以定位贡献。

- Llumnix：源端执行与已有 KV 复制重叠，多阶段追赶后接管；不能把此协议写为新机制。https://arxiv.org/html/2406.03243v1
- SAGA：工作流感知复用、工具期预取、work stealing 与 Agent 完成时间；不能仅用 reactive/proactive 区分。https://arxiv.org/html/2605.00528v1
- DualMap：双候选、SLO 感知路由、热点重平衡和弹性映射，是强 routing 基线。https://arxiv.org/html/2602.06502v1
- SmartGen：已有选择性传输、解码期按需获取和推测传输，要求进一步逐项比较提前消费的精确性、消费粒度与场景。https://arxiv.org/abs/2607.28150
- Mooncake TENT：已有 deadline admission 和 RDMA slice 仲裁，单纯 deadline-aware 不是新颖性。https://kvcache-ai.github.io/Mooncake/design/tent/deadline-scheduling.html
- Pallas：已有预测目标、提前准备与源端执行重叠，场景是 AI-RAN handover。https://arxiv.org/abs/2608.16477

候选贡献是上述三环节针对 Agent 多轮执行的闭环协调。需要证明其联合决策与渐进协议带来的收益超过已有策略组合；目前不写“首次”。

## 10. 论文必须回答的三件事

1. **为什么需要改变状态布局？** 在相同 GPU、内存、到达和输出长度下，证明优秀 routing / 共享缓存策略仍会因准备、排队或容量错配付出明显代价。真实热点与 worker 退出分别是负载变化和强制布局变化场景。
2. **为什么现有迁移/预取不够？** 证明完整迁移屏障、准备时机误判、资源竞争或状态边界限制中的具体问题；评估强迁移与预取基线。
3. **为什么联合设计有效？** 对齐路由比较有无准备，对齐目标比较完整与渐进接管，对齐内存预算比较准备策略；记录所有任务与邻居的收益、代价和失败。

主要指标是多轮任务完成时间及满足规定服务目标的 goodput；同时报告完整 TTFT、TPOT、token 间隔尾延迟、迁移中断、重算 token、网络字节、源端实际释放和峰值双份状态占用。固定指标和工作负载后再比较。

## 11. 执行优先级

先修复评测并确认强路由下的机会，再验证非空目标安全导入与繁忙源的状态固定。已有 progressive 可用于专门的依赖重叠实验；当前同步 DCU 路径不能直接代表这套完整设计。

若强基线已经消除主要等待，这个工作负载应如实报告为低收益区间。若真实重配置下仍有显著准备阻塞，再用这套协议和资源调度回答如何消除它。投稿定位由最终贡献和规模验证决定。

## 12. 2026-10-09 新实验

新回放 p06 修正了在途预留、完整计时与失败分母，并同时记录 TPOT、token 间隔和 SLO 网格。27 个正式/控制试验共 1,440 个请求，0 个请求错误。

受控 64K 共享前缀 fan-out、连接预建、1s 准备窗口下：16 分支/上限8，复制相对最快不准备策略的 wall 约减少15.8%；上限提高64后，同样16分支只减少4.1%；64分支/上限64时，相对 balanced 约减少14.3%，请求goodput约增加16.6%。TPOT基本相同，未验证decode加速。引擎实际64个并发decode由日志确认。

传输状态摘要与相同单请求批次的64-token续算输出对照通过。完整成本包括约0.81s/2.37GB的复制和31–32s的建链；若建链暴露且只服务一次事件，抵消本轮所有服务收益。

这支持“准备改变执行选择”和一次准备跨请求复用的动机。大幅sticky差距的一部分来自并发上限，不能作为固有矛盾。连续多前缀、繁忙源、非空目标与完整强基线仍是下一阶段的验证问题。
